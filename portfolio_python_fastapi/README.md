# JC LoanDoc - 대출 서류 패키지 페이지 분류 데모

여러 종류의 대출 서류가 페이지 단위로 무작위로 섞인 PDF 패키지를 입력받아,
각 페이지의 문서 유형(URLA_1003 / INCOME_DOC / CREDIT_REPORT / TITLE_REPORT /
OTHER)을 판별하고 문서 단위로 그룹핑하는 파이프라인입니다. 자동 인수심사(AUS)로
가는 처리 흐름에서 데이터 추출 앞단에 놓이는 문서 분류/스플리팅 문제를 다룹니다.

실서비스가 아닌 포트폴리오 데모입니다. 화면과 리포트에 보이는 데이터는 전부
코드로 생성한 **합성 픽스처**로, 공개 표준 양식의 명칭·상용구만 쓰고 실서류·
실기업 상호·개인정보를 담지 않습니다. 업로드 파일은 처리 후 즉시 삭제되고
서버에 남지 않습니다.

## 1. 화면 구성 (2단)

| 표면 | 내용 |
|---|---|
| 업로드 데모 (`/`) | PDF 를 올리면 페이지별 판정·근거·문서 그룹핑 타임라인을 즉시 렌더링. 방문자용 [합성 샘플 패키지](demo/demo_package.pdf)(16p, `/sample.pdf`)를 함께 제공합니다 |
| 완성형 리포트 (`/report`) | 같은 샘플을 파이프라인으로 돌린 자기완결형 정적 HTML([demo/report.html](demo/report.html)) - 요약 지표, 그룹핑 타임라인, 페이지별 결과표, 논리 문서 재구성까지 산출물의 완성형. **룰 단독 기준**이라 업로드 데모에서 캐시 재생으로 AI 판정이 붙는 페이지(p15)가 여기서는 저신뢰로 남습니다 - 룰 레이어 단독의 도달점을 보이는 것이 이 자산의 역할입니다 |

두 자산은 `python scripts/make_demo_package.py` 로 재생성하며, 픽스처와 룰
레이어 모두 결정적이라 재실행 산출물이 바이트까지 같습니다.

## 2. 실행 방법

```bash
cd portfolio_python_fastapi
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-web.txt      # 파이프라인만 쓰면 requirements.txt
uvicorn webapp.app:app --port 8000       # http://localhost:8000
```

- CLI: `python -m loandoc classify --pdf <입력.pdf> --out <디렉토리> --no-llm`
- 테스트: `pip install -r requirements-dev.txt && python -m unittest discover -s tests`
- E2E 스모크(합성 픽스처, 외부 데이터 불필요): `python scripts/ci_smoke.py`
- 컨테이너: `docker build -t loandoc . && docker run --rm -p 8000:8000 loandoc`

## 3. 아키텍처 - 2단 하이브리드

```
PDF ─ 인입 게이트(매직넘버, 파싱 전 거절) ─ pypdf 텍스트 추출
   ├─ 1차: 시그니처 룰 채점 → 점수·마진 임계치로 "확정/저신뢰" 판별
   ├─ 2차: 저신뢰 페이지만 LLM 폴백 (텍스트 또는 pypdfium2 렌더링 비전)
   ├─ 그룹핑: 연속 라벨 run + 내부 페이지 번호("Page N of M") 논리 문서 재구성
   └─ 산출: JSON/CSV, 자기완결 HTML 리포트, 타임라인 시각화(PNG)
```

- **룰이 1차인 이유** - 대상 서류가 표준 양식(Form 1003, 타이틀 커밋먼트, IRS
  전사본 등)이라 고정 문구가 강한 신호입니다. 결정적이고, 무비용이고, 판정
  근거(매칭 시그니처 id)가 페이지 단위로 남아 감사할 수 있습니다.
- **LLM 은 폴백인 이유** - 전 페이지 LLM 은 비용·지연이 페이지 수에 비례하고
  근거가 모델 응답에 갇힙니다. 텍스트가 없는 스캔·헤더가 이미지뿐인 페이지처럼
  룰이 원리적으로 못 보는 소수만 맡깁니다. 두 판정은 독립입니다(룰 점수를
  프롬프트에 넣지 않아 앵커링을 피합니다).
- **이 배포는 LLM 키를 두지 않습니다** - 공개 데모 서버에 상용 API 키를 두면
  비용·남용 표면이 생깁니다(이 포트폴리오의 시크릿 없음 원칙). 키를 설정하고
  실행하면(로컬) LLM 폴백 경로가 그대로 살아납니다.
- **그래도 배포에서 실제 판정을 봅니다 - 응답을 커밋했기 때문입니다**
  ([demo/llm-cache](demo/llm-cache)). 키가 없으면 LLM 폴백이 무엇을 하는지
  화면으로 보일 방법이 없어, 코드는 실재하는데 주장만 남습니다. 키를 가진
  사람이 한 번 받아 온 응답을 요청 해시별로 저장해 커밋하고, 무키 서버는
  그것을 재생합니다(`LlmClassifier(cache_only=True)`). 캐시가 곧 재현성
  장치이자 산출물입니다.
  **경계는 화면이 말합니다**: 동봉 샘플은 "실제 Claude 응답을 캐시에서 재생",
  직접 올린 PDF 는 캐시에 없으므로 "룰 단독으로 판정". 재생을 실시간 호출인
  척하지 않는 것이 이 장치의 전제입니다.

  ```bash
  # 키가 있는 로컬에서 1회. 이 스크립트만 실제 API를 부릅니다.
  ANTHROPIC_API_KEY=sk-ant-... python scripts/make_llm_cache.py
  git add demo/llm-cache && git commit
  ```

## 4. 설계 판단

- **인입 게이트 (파싱 전 내용 검증)** - 실무에서 이 파이프라인의 입력은 신뢰
  불가 업로드이고 확장자는 위조됩니다. 판정 권한을 파일 내용(`%PDF-` 매직)에
  두고, 실행파일 시그니처(MZ/ELF/shebang)는 구체적 사유로 거절하며, 확장자
  불일치는 경고로만 남깁니다. PDF 파서 자체가 공격 표면이라 파서에 닿기 전에
  싸게 거릅니다. 파일 확장자 차단 데모(`portfolio_jquery_spring`)와 같은
  원칙("내용 검사를 정책 검사보다 먼저")의 파이썬판입니다.
- **동기 데모 API 의 자원 상한** - 업로드 100MB·페이지 300 상한·렌더 픽셀
  클램프·LLM 모델 allowlist. 신뢰 경계 밖 입력이 CPU·메모리·비용을 무제한
  끌어가지 못하게 하는 방어선이고, nginx 엣지에서 용량·rate limit 을 한 번 더
  조입니다. 실무 규모라면 동기 API 가 아니라 S3 → 큐 → 워커 비동기 배치가
  맞고, 페이지 단위 독립 판정과 파일 해시 캐시가 그 스케일아웃에 그대로
  쓰입니다.
- **ML 분류기를 쓰지 않은 이유** - 라벨된 데이터가 수십 페이지 규모인 문제에서
  학습 기반 분류기는 과적합이 자명하고, 유형 추가마다 재학습이 필요합니다.
  시그니처 룰은 같은 지식을 학습 없이 명시적으로 담고 페이지 단위로 오류를
  설명할 수 있습니다. 유형 추가 = 시그니처 데이터 몇 줄 + LLM 프롬프트의 라벨
  정의 추가입니다.
- **데이터 취급** - 업로드는 요청 처리 동안 임시 디렉토리에만 존재하고 응답 후
  삭제, 서버측 추출 캐시는 기본 비활성(서류 파생 텍스트를 서버에 남기지 않기
  위함)입니다. 데모 자산은 전부 합성 픽스처([scripts/synth.py](scripts/synth.py))
  에서 나오며, 픽스처는 공개 표준 양식의 상용구만 씁니다.
- **재현성** - 룰 레이어는 완전 결정적이고, 픽스처 PDF 는 타임스탬프·난수 없이
  손조립되어 같은 입력이면 산출물이 바이트까지 같습니다. `scripts/ci_smoke.py`
  가 2회 실행 diff 로 이를 검사로 고정합니다.

## 5. 테스트

`python -m unittest discover -s tests` - 59개(외부 데이터 불필요).

| 스위트 | 내용 |
|---|---|
| 룰·그룹핑·재구성 | 시그니처 채점, 신용정보사 콤보 가점, run 그룹, 페이지 번호 기반 재구성(중복 번호 분리 포함) |
| 인입 게이트 | 매직넘버 거절(실행파일 사유 명시), 빈 파일, 확장자 불일치 경고 |
| 속성 기반(hypothesis) | 임의 텍스트 무크래시·라벨 폐쇄성, 정규화 멱등성, 그룹핑 분할 불변식 |
| HTML 리포트 | 섹션·유형 색 고정, LLM 사유 이스케이프, 정답 대조 섹션 |
| 웹 래퍼 | 분류/거절/상한/모델 allowlist, 귀속·고지 렌더, 샘플·리포트 라우트 |

별도로 `scripts/ci_smoke.py` 가 합성 픽스처로 게이트 거절 → E2E 산출물 생성 →
라벨 일치 → 재현성(바이트 동일)을 검사합니다.

## 6. 한계와 다음 단계

- **시그니처 일반화** - 시그니처는 표준 양식 상용구 중심이라, 벤더 고유 서식
  비중이 큰 실패키지에서는 룰 커버리지가 떨어지고 폴백 비율이 올라갑니다.
  완화책은 폴백 비율 모니터링 → 시그니처 승격 루프입니다.
- **배포 데모의 저신뢰 잔여** - LLM 키가 없는 배포에서는 무텍스트 페이지가
  저신뢰 추정으로 남습니다. 의도된 트레이드오프이며 화면에 그대로 표시됩니다.
- **재구성 휴리스틱** - 내부 페이지 번호가 없는 문서는 순서 복원이 안 되고,
  같은 쪽수의 동종 문서가 여럿이면 등장 순서로 추정합니다. 문서 내 필드(연도·
  섹션 번호)를 보조 키로 쓰는 것이 다음 단계입니다.
