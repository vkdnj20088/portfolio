# DESIGN.md - JC Ticker 실시간 관심종목 설계 문서

> 대상 코드: 이 저장소 전체. `lib/feed/`(결정론적 데이터 소스) 위에 쌓은
> `domain / data / state / ui / baseline` 계층의 설계 결정과 근거를 기록한다.
> 구체적 최적화 값(통지 주기 등)의 근거 수치는 [PERF.md](PERF.md)를 따른다.

---

## §1. 설계 요약 (한 장)

```
lib/feed/  MarketFeed ──(List<QuoteTick> 60Hz, 지연/역순/halt/에러 포함)──>
              │
lib/data/  MarketRepository        <- feed 구독은 앱 전체에서 이 1곳
              │  - onError 흡수 -> FeedHealth(degraded/healthy, 히스테리시스)
              │  - 스냅샷 적재 + 배치 전달
              ▼
lib/state/ QuoteStore              <- 단일 진실 공급원, feed->도메인 변환 경계
              │  - 종목별 timestampMs 단조 강제 (역순 tick 기각)
              │  - 3단 상태 (unknown/active/halted)
              │  - 값 불변 tick -> 통지 생략 (ts만 전진)
              │  - 증분 시총 합계 (BigInt 델타 누적)
              │  - RankIndex: (등락률 desc, 코드 asc) 전순서를 O(log n) 증분 유지
              │  - GatedNotifier: 값 갱신과 통지 분리 (범위 제한/주기 flush)
              ├──> 종목별 ValueListenable<Quote> x2,000
              ├──> marketCapSum (BigInt), top20 (순서 바뀔 때만 통지)
              │
lib/state/ SearchModel             <- 정적 인덱스(초성열) 1회 구축, tick과 무관
              │
lib/ui/    WatchlistPage           <- tick으로 페이지 rebuild 없음
              ├ SummaryBar / HealthBanner / Top20Strip (집계 notifier 구독)
              ├ ListView.builder(itemExtent 고정)
              │    └ QuoteRow = RepaintBoundary + 자기 종목 notifier만 구독
              └ DetailPage          <- 진입 시 통지 범위를 {해당 종목}으로 제한
                   └ Sparkline (고정 용량 링버퍼 + CustomPainter)
```

설계 원칙 셋:

1. **정합성은 도착 즉시, 화면은 프레임 단위로.** tick은 배치 도착 즉시 상태에
   반영해 상태가 항상 최신/정합하도록 유지하고, 화면 전파(통지)만 제어한다.
   상태와 통지를 분리했기 때문에 성능 최적화가 정합성을 침식하지 않는다.
2. **성능을 가르는 것은 rebuild 전파 범위다.** 이 워크로드는 연산량이 아니라
   (PERF.md §2: 배치당 적용 비용 us 수준) "tick 1건이 몇 개의 위젯을 다시
   그리게 하는가"가 병목이다. 모든 구독을 종목/집계 단위로 쪼갰다.
3. **집계는 마지막으로 알려진 가격 기준, 상태는 표시에만 관여.** halt/unknown을
   집계마다 다르게 취급하면 일관성 논리가 복잡해진다. 단일 원칙으로 통일했다 (§5).

## §2. 계층과 경계

| 계층 | 파일 | 책임 | 알지 못하는 것 |
|---|---|---|---|
| feed | `lib/feed/*` | 원시 데이터 소스 (결정론 시뮬레이터) | 상위 계층 전부 - 실피드 교체 경계 |
| data | `data/market_repository.dart` | feed 구독 수명, 스트림 에러 흡수/복구 판정 | 위젯, 화면 구조 |
| domain | `domain/quote.dart`, `domain/chosung.dart` | 앱이 소비하는 모델(3단 상태/파생값), 초성 매칭 | Flutter 전체 (순수 Dart) |
| state | `state/quote_store.dart` 외 | 정합성 강제, 증분 집계, 통지 제어, 검색 상태 | feed의 존재 (배치를 받을 뿐), 화면 구조 |
| ui | `ui/*` | 표시와 구독 연결 | feed 타입 (Quote/집계 notifier만 소비) |
| baseline | `baseline/*` | PERF.md 비교 기준 (의도적 순진 구현) | - (개선 대상 아님) |

**feed->도메인 변환 경계는 `QuoteStore.applyBatch` 한 곳이다.**
raw `QuoteTick`이 이 함수를 지나면서 (a) timestamp 검증을 통과하고 (b) 3단
상태로 해석되고 (c) 불변 `Quote`로 변환된다. 프레젠테이션은 feed 타입을 모른다
(`SymbolInfo`는 불변 메타데이터라 그대로 노출 - 변환해도 얻는 것이 없다).
경계를 한 곳으로 모은 이유: 지연/역순/halt/값 불변 처리 규칙이 여러 곳에
흩어지면 "어떤 화면은 역행하고 어떤 화면은 아닌" 종류의 버그가 생긴다.
같은 이유로 **feed 구독도 repository 하나만** 갖는다. 화면이 각자 feed를
구독하면 (broadcast라 가능은 하다) 정합성 판정이 구독자 수만큼 중복된다.

상태관리 라이브러리는 쓰지 않았다(§7). 이 문제의 올바른 단위는 "종목별 구독"
인데, 그것은 `ValueListenable` 2,000개로 정확히 표현되고, 라이브러리는 그 위에
추상화 비용만 얹는다.

## §3. 도메인 모델 - 3단 거래 상태 (unknown / active / halted)

feed의 `QuoteStatus`는 2단(active/halted)이지만 도메인은 3단이다. 근거는 feed
주의사항 세 가지의 논리적 귀결이다:

- 정지/해제는 **그 종목의 tick이 와야만** 관측된다 (별도 이벤트 없음)
- 해제는 명시 신호가 없고 **다음 active tick**으로만 안다
- `initialSnapshot()`에는 정지 정보가 **없다**

따라서 구독 직후 ~ 첫 tick 사이에는 정지 여부를 알 수 없는 구간이 반드시 존재하고,
이를 `active`로 때려넣으면 "정지 중인데 정상처럼 보이는" 창이 생긴다.
`TradingState.unknown`으로 명시했다. 상태 전이는 단순하다:

```
unknown ──첫 tick(active)──> active <──active tick── halted
unknown ──첫 tick(halted)──> halted <──halted tick── active
```

전이는 timestamp 검증을 **통과한** tick만 일으킨다. 부수 효과로 좋은 성질 하나:
halted tick의 timestamp는 항상 현재 시각이므로, 정지 직전에 생성됐다가 지연
도착하는 active tick(과거 ts)은 역순 기각 규칙이 자동으로 걸러낸다 - 상태
정합성을 위한 별도 장치가 필요 없다 (테스트: `store_reconcile_test.dart`).

**UI 표기 판단**: 목록 행은 halted만 뱃지로 구분한다. unknown까지 뱃지를 달면
구독 직후 2,000행 전부에 "확인 중"이 붙는 노이즈가 되고, 그 구간은 종목당 평균
수백 ms에 불과하다(PERF.md §2, 종목당 tick 간격 ~270ms). 상세 화면은 한 종목을
깊게 보는 자리이므로 unknown도 "상태 확인 중"으로 정직하게 표기한다.

## §4. 에러 모델과 성능-신선도의 선

### 지연/역순 tick

종목별 `lastTs`를 유지하고 `tick.timestampMs <= lastTs`면 **tick 통째로 기각**
한다. 가격만 지키고 거래량을 반영하는 식의 부분 수용은 하지 않는다 - 지연
tick은 생성 시점의 값이므로 **거래량도 과거값**이고, 부분 수용은 "가격은
새것/거래량은 헌것" 조합을 만든다. `<=`(등호 포함)로 재적용도 막아 멱등이다.
기각률은 실측 0.044%(PERF.md §5)로, 버려서 잃는 정보는 사실상 없다.

### 값 불변 tick

가격이 clamp(±30%)에 고착되거나 랜덤워크 step이 0이어도 tick은 계속 온다.
가격/거래량/상태가 모두 기존과 같으면 **통지를 만들지 않고 timestamp만
전진**시킨다 (`stats.unchanged`). timestamp를 전진시키는 것이 중요하다:
그래야 그 사이 시각의 지연 tick이 올바르게 기각된다. 주의할 함정 하나 -
"가격 불변"과 "값 불변"은 다르다. 가격이 그대로여도 거래량은 대개 증가하므로
(halted tick만 완전 동결), 필드별 변경 플래그로 판정한다: 가격 변경 ->
행 통지 + 시총 델타 + 순위 갱신 / 거래량만 변경 -> 행 통지만 / 완전 불변 -> 무통지.

### 일시적 스트림 에러

`listen`의 `cancelOnError` 기본값(false)을 유지하고 **onError를 반드시 단다**
(안 달면 broadcast 스트림 에러가 unhandled로 새어나간다 - "무시"조차 구현이
필요하다). 에러는 `FeedHealth`(degraded/healthy + 누적 횟수)로 흡수해 배너로
표시하고, 구독은 그대로 살아 다음 배치에서 복구한다.

복구 판정에 **히스테리시스**를 넣었다: 마지막 에러 후 1초 이상 조용한 상태에서
정상 배치가 도착해야 healthy로 되돌린다. `transientErrorProbability`를
0.1로 올리면 에러가 평균 ~170ms 간격으로 오는데, "배치=복구/에러=강등"을
즉시 반복하면 배너가 프레임 단위로 점멸한다. 히스테리시스 덕에 불안정 구간
동안 배너가 안정적으로 유지되다가, 실제로 잠잠해지면 내려간다.
재시도 버튼은 두지 않았다 - 이 에러 모델은 정의상 자동 복구되며(스트림이
닫히지 않음), 사용자가 할 수 있는 유효한 행동이 없다.
(회귀 테스트: `error_recovery_test.dart`, p=0.1로 구독 생존/복구 검증)

### 성능-신선도 - 어디에 선을 그었나

요구: 보이는 행은 최신 tick 도착 후 **200ms**(=60Hz 기준 12프레임) 안에 반영.

선택: **통지 주기를 두지 않는다 (배치 도착 즉시 통지).** 배치는 최대 60Hz로
도착하고 Flutter는 어차피 프레임당 1회만 build하므로, 즉시 통지는 사실상
"프레임 정렬 coalescing"과 같다. 화면 반영 지연은 최대 1프레임(약 16ms)으로
200ms 예산의 8%만 쓴다.

이것이 공짜인 이유는 부하 구조에 있다(PERF.md §2): 종목당 tick은 평균
3.7건/s이고 화면에 보이는 행은 ~15개라 **프레임당 보이는-행 갱신은 평균
1건 남짓**이다. 통지를 모아서 얻을 것이 거의 없다. 실제로 통지 주기
0/50/100/200ms를 스윕한 결과(PERF.md §4) 주기를 키우면 평균만 내려가고
꼬리(p99)는 오히려 나빠져(idle 8.79->11.57ms, search 7.34->13.22ms - 모인
flush가 스파이크를 만든다),
신선도가 가장 좋은 0ms를 택했다. 즉 이 선택은 "감"이 아니라 (a) 부하 산정
(b) 스윕 실측 두 근거 위에 있다. 만약 배치 빈도가 10배(600Hz)로 오르면 같은
스윕을 다시 돌려 주기를 올리면 되도록, 주기는 `NOTIFY_MS` 빌드 플래그로
파라미터화되어 있다.

**만능이 아닌 지점**: 시총/Top-20 notifier가 60Hz로 통지하므로 요약 위젯들이
최대 60fps로 rebuild된다. 이 위젯들은 텍스트 몇 개 수준이라 실측상 문제가
없지만(PERF.md §4), 요약 영역이 무거워지면 집계 통지만 별도 주기로 낮추는
것이 다음 손잡이다 (구조상 GatedNotifier라 즉시 가능).

## §5. 집계/검색 정책

### halt/unknown의 집계 반영 - 단일 원칙

> **모든 집계는 "마지막으로 알려진 가격"을 사용한다. 거래 상태는 집계에서
> 종목을 넣고 빼지 않고, 표시(뱃지/색)에만 관여한다.**

| 집계 | halted | unknown | 근거 |
|---|---|---|---|
| 시가총액 합계 | 직전가로 **포함** | 스냅샷 가격으로 **포함** | 정지되어도 회사의 시가총액이 0이 되지 않는다. 제외하면 정지/해제 순간 합계가 수십조 단위로 점프해 오히려 오해를 부른다 |
| Top-20 | 동결 등락률로 **포함** + 타일에 "거래정지" 표기 | 등락률 0%로 자연 포함 | 정지 직전 +29%였던 종목이 순위에서 증발하는 것은 정보 손실. 동결 등락률은 값이 변하지 않으므로 rank thrashing도 일으키지 않는다 |
| 표시 종목 수 | **포함** | **포함** | "표시 중" = 화면에 행이 있는 종목. 정지 종목도 행은 표시된다 |

두 집계(시총/Top-20)의 처리가 **같은 원칙**에서 나오므로 별도의 일관성 논리가
필요 없다 - 이것이 이 원칙을 택한 가장 큰 이유다. 기각한 대안(halted 제외)은 §8-6.

### 필터와 집계 기준

- **표시 종목 수 = 필터 통과 수** (표시 정의).
- **시총 합계/Top-20 = 전체 2,000종목 기준** (필터 무관). 요약 영역은 "시장
  전체 상황판"이고 검색은 "목록을 좁혀 보는 렌즈"라는 역할 구분이 근거다.
  화면에도 "(전체)"로 명시했다. 필터 기준 집계는 §8-5에서 기각.
- 필터 아웃된 종목의 갱신 비용: 상태 반영(맵 갱신/집계)은 계속되지만 - 전체
  기준 집계가 정확하려면 필요한 비용이다 - **위젯 비용은 0**이다. 필터 아웃
  행은 아예 mount되지 않으므로 notifier에 리스너가 없고, 통지는 리스너 없는
  ChangeNotifier 호출(무시)로 끝난다.

### 초성 검색

- **정적 인덱스**: 종목명/코드는 불변이므로 초성열(`한빛전자->ㅎㅂㅈㅈ`)을
  시작 시 1회만 추출해둔다. 필터 재계산은 **질의가 바뀔 때만** 일어나고 tick과
  완전히 무관하다 - "고빈도 tick 중의 필터링" 요구는 최적화로 푼 것이 아니라
  **의존성 자체를 제거**해서 풀었다 (회귀 테스트: `chosung_search_test.dart`의
  "필터 결과는 tick 유입과 무관하다").
- **매칭 규칙**: 종목명 부분일치 OR 코드 부분일치 OR (질의가 순수 자음일 때)
  초성열 부분일치. 접두가 아닌 부분일치로 통일한 이유: "전자" 같은 접미 검색이
  자연스럽고, 초성도 같은 의미론을 갖는 것이 예측 가능하다.
- **직접 구현 (라이브러리 미사용)**: 필요한 전부가 `(코드포인트-0xAC00)~/588`
  -> 초성 19자 테이블 조회다 (`domain/chosung.dart`, 실질 ~30줄). 한글 검색
  라이브러리들은 중성/종성 분해, 퍼지 매칭 등 이 데모에 불필요한 기능을
  포함하며, 핫패스에 검증 불가능한 외부 코드를 두지 않는 원칙(§7)을 따랐다.
- **debounce 120ms**: 스캔 비용(2,000건 문자열 검사, us~수십 us)이 아니라
  **필터된 ListView 재구성**을 타이핑 burst당 1회로 모으기 위한 값이다.
  120ms는 연속 타이핑(초당 5~10타)을 묶으면서 입력 종료 후 지연은 체감되지
  않는 선이다. 입력 중에도 tick 신선도 제약은 그대로 유지된다 - 필터와 tick
  경로가 분리되어 있으므로 debounce는 신선도에 영향을 주지 않는다.

### Top-20 - 매 tick 전체 재정렬 없이

`RankIndex`가 (등락률 내림차순, 코드 오름차순)의 **전순서를 SplayTreeSet으로
상시 유지**한다. tick 하나는 종목 하나의 등락률만 바꾸므로 제거->갱신->재삽입
O(log 2000 = 약 11)이면 되고, Top-20 조회는 트리 앞 20개 순회다. 전체 재정렬은
어떤 경로에도 없다. 정확성은 브루트포스 전체 정렬과의 등가성 테스트로 보증한다
(`aggregates_test.dart`, 실제 feed 300배치).

- **동률 tiebreak**: clamp로 등락률이 정확히 같아진 종목들은 코드 오름차순으로
  고정된다. Dart `List.sort`가 unstable이라 생기는 rank thrashing(순위 무변인데
  표시 순서가 매 tick 뒤바뀜)을 comparator 수준에서 차단한 것이다.
- **통지 축소**: Top-20 notifier는 **순서가 바뀔 때만** 통지한다. 타일 안의
  등락률 텍스트는 각 타일이 자기 종목 notifier를 구독해 갱신하므로, 순위가
  안 바뀌는 프레임에는 스트립 구조가 rebuild되지 않는다.
- **key와 숫자 폭**: 행과 타일의 key는 불변 종목코드다(`row-<code>`,
  `top-<code>`). 순위 재배열/필터 변경이 Element와 State의 이동으로 처리되며,
  가격/순위 같은 시세 파생값을 key로 쓰면 tick마다 행이 파괴/재생성된다.
  숫자 텍스트는 전부 tabular figures(고정 폭 숫자)다 - 비례 숫자면 자릿수가
  바뀔 때마다 텍스트 폭이 변해 갱신마다 행 layout이 다시 돈다.

### 시가총액 합계 - 정수 델타 누적 (합계만 BigInt)

가격은 호가단위 반올림된 정수값이므로 `가격 x 상장주식수` 합을 **정수로** 유지하고
가격 변경 시 `(신-구)x주식수` 델타만 더한다. double 누적이면 1e17 스케일에서
반올림 오차가 쌓이는지 논증해야 하지만, 정수 연산은 그 논증 자체가 필요 없다.
처음에는 int 하나로 들고 있었는데(최대 합계 ~1.3x10^17 < int64 상한), 그것은
**네이티브 전제**였다 - JS 컴파일(web)에서는 정수 정밀이 2^53까지라 합계가
그 위에서 깨진다. web 타깃을 추가하면서 §10 표의 해당 행대로 **누적 변수만
BigInt로** 바꿨다: 종목당 곱(~2.5x10^14)과 델타(~1x10^12)는 2^53 안이라 int
연산으로 만들고, 상한을 넘는 것은 합계뿐이므로 BigInt 연산은 tick당 덧셈
1회다. 등가성은 전량 재계산과의 일치 테스트로 보증한다 (`aggregates_test.dart`).

## §6. 화면 2 (상세)와 구독 수명

**feed 구독은 상세 진입 후에도 repository 하나 그대로다.** 대신
`QuoteStore.restrictNotifications({해당 종목})`으로 **통지 범위**를 제한한다:

- 값 반영/집계는 계속된다 -> 돌아왔을 때 상태가 이미 최신이고, 전체 기준
  집계도 끊기지 않는다.
- 목록/요약/Top-20 위젯은 통지를 받지 못하므로 rebuild 비용이 0으로 떨어진다
  (실측: PERF.md §4의 detail 구간).
- 복귀 시 `restrictNotifications(null)` -> 밀린 통지가 한 번에 flush되어 즉시
  최신 화면이 된다.

"구독을 끊는" 대안과 비교하면, 이 방식은 복귀 시 재구독/재스냅샷 비용과
"부재 중 halt 전이를 놓치는" 문제가 없다. 통지 범위 변경 시 flush는
마이크로태스크로 이연한다 - restrict/restore가 위젯 initState/dispose(트리 잠금
구간)에서 불리기 때문에 그 자리에서 notify하면 framework 예외가 난다 (실제로
개발 중 위젯 테스트가 이 경로를 잡아냈다).

같은 원리를 **앱 백그라운드 구간에도 적용**했다: 라이프사이클 옵저버가 화면이
사라지면 통지 전체를 멈추고(`setNotificationsPaused`), 복귀 시 일괄 flush한다.
통지 범위(상세 화면)와는 독립된 축이라 서로를 덮어쓰지 않는다 - 상세를 띄운 채
백그라운드에 다녀와도 두 제한이 각자 복원된다 (`lifecycle_test.dart`).

**스파크라인**: 최근 체결가를 고정 용량(180) 링버퍼에 유지 - O(1) 추가, 재할당
없음, 무한 성장 없음. 캔버스 높이도 140으로 고정해, 데이터가 쌓여도 컨테이너가
늘며 아래 내용을 밀어내는 일이 없다. 축은 미니 차트 관행대로 눈금자 없이 스케일
단서만 캔버스에 직접 그린다 - 우측에 버퍼 내 고/저와 전일 종가, 좌하단에 표본
수("최근 체결 N건"). 가로축을 시간 눈금으로 만들지 않은 것은 판단이다: 링버퍼는
가격만 저장하고(시각 미저장), 체결 간격이 불균일한데 등간격으로 그리면서 시간
눈금을 붙이면 오히려 왜곡이 된다 (§8-7의 "데이터를 왜곡하지 않는 표현" 원칙).
repaint는 CustomPainter의 `repaint` Listenable로만
일으키며, **가격이 실제로 바뀐 tick**(및 정지-재개 전이)에만 트리거한다.
거래량만 바뀐 tick/값 불변 tick으로는 선을 다시 그리지 않는다.
히스토리의 수명은 화면과 같다 - 재진입하면 그 시점부터 다시 쌓인다. 보지 않는
2,000종목의 버퍼를 상시 유지하는 대안은 메모리와 적용 경로 비용을 화면 밖에서
계속 내는 구조라 기각했다 (전 종목 이력이 제품 요구가 되면 스토어 쪽 링버퍼로
옮기는 것이 확장 지점이다).

**시가/고가/저가의 정의**: feed에는 당일 이력이 없으므로 "구독 시작(스냅샷)
이후 관측 기준"으로 정의하고 화면에 그 사실을 명시했다. 시가=스냅샷 가격,
고가/저가=이후 수용된 tick의 극값(정지 tick은 가격이 동결이라 자연히 영향 없음).

## §7. 의존성 선택

**런타임 외부 패키지 0개** (dev: `flutter_test`/`integration_test`/`flutter_lints`뿐).

- 상태관리(Riverpod/Bloc 등) 미사용: 이 문제의 핵심 단위인 "종목별 구독"은
  `ValueListenable`이 정확히 그것이다. 라이브러리를 얹어도 같은 구조를 만들게
  되며, 15,000건/s가 지나는 핫패스에 블랙박스가 없는 쪽이 진단과 설명
  모두에 유리하다. (Riverpod `select` 기반 대안은 §8-2에서 함께 논한다)
- 차트 라이브러리(fl_chart 등) 미사용: 요구는 폴리라인+기준선이 전부다.
  CustomPainter ~80줄이 매 tick 전체 차트 재구성 같은 라이브러리 내부 비용도
  피한다.
- intl 미사용: 필요한 포맷이 콤마/부호/조/경 3종뿐이라 직접 구현이 더 작다.

## §8. 검토했지만 기각한 대안

### 8-1. 스트림 레벨 throttle/샘플링 (성능 - 정합성/신선도 상충 대안)

repository에서 배치를 모아 5~10Hz로 다운샘플해 하위 계층 전체의 압력을 줄이는,
가장 흔한 처방. **성능만 보면 유리**하다 - 통지/집계 빈도가 1/6~1/12로 준다.
기각 이유:
- **신선도 하한이 구조화된다.** 10Hz면 최악 100ms+프레임이 상시 지연으로 깔리고,
  주기를 올리면 성능 이득이 사라진다. 200ms 예산의 절반을 아키텍처가 선점하는 셈.
- **정합성 처리와 얽힌다.** 샘플링 창 안에서 같은 종목의 지연 tick과 정상 tick이
  함께 잡히면 "창 내 최신 선별" 로직이 timestamp 검증을 중복 구현하게 된다.
  halt 전이 tick이 샘플링에 씹히면 상태 전이가 늦는 문제도 생긴다.
- **결정적으로, 실측이 불필요함을 보였다.** 즉시 반영 경로의 배치당 적용 비용이
  us 수준(PERF.md §2)이라, 다운샘플이 절약하는 것이 애초에 병목이 아니다.
채택안(즉시 적용 + 통지만 제어)은 상태는 항상 최신으로 두므로 이 상충 자체를
해소한다 - "성능을 위해 신선도를 얼마나 팔까"가 아니라 "팔 필요가 없는 구조"를
택한 것이 §4의 결론이다.

### 8-2. 불변 전체 리스트 상태 방출 (단일 상태 스트림형 아키텍처)

Bloc/Riverpod에서 흔한 `State(List<QuoteView> 2000)`를 배치마다 새로 emit하는
설계. 선언적이고 테스트가 쉬우며 팀 표준으로 삼기 좋다. 기각 이유: 배치마다
2,000개 뷰모델 리스트 재구성(최대 60Hz)이 필요하고, 소비 측에서 "무엇이
바뀌었나"를 다시 diff해야 한다 - 생산 시점에 이미 알고 있던 변경 정보를 버렸다가
재발견하는 구조. `select`/`Equatable`로 rebuild를 줄여도 비교 연산 자체가 종목
수x빈도로 늘어난다. baseline이 이 계열의 극단형이며, 실측 격차는 PERF.md §4.

### 8-3. Isolate로 tick 처리 오프로딩

"15,000건/s"라는 숫자만 보면 워커 isolate가 당연해 보인다. 기각 이유: 실측
적용 비용이 배치당 215.9us(debug JIT 기준, profile은 그 이하 - PERF.md §2)로
16.7ms 프레임 예산의 ~1.3%에 불과하다. 상한 부하(15,000건/s)를 지속시켜도
배치당 424.2us, 한 코어의 2.55%다 (PERF.md §6). isolate로 옮기면 배치/결과를 매초 수천
건 직렬화/복사해 넘겨야 하고(SendPort 전송 비용), UI가 구독하는 notifier는
결국 메인 isolate에 있어야 하므로 "결과 반영" 단계가 그대로 남는다. 비용은
추가되고 병목은 옮겨지지 않는다. 재검토 조건: 파생 계산이 실제로 무거워질 때
(예: 전 종목 기술지표 계산).

### 8-4. Top-20을 "주기적 전체 재정렬"로 유지

구현이 단순한 대안: flush마다 2,000건 전체 정렬. 2,000 log 2,000 = 약 2.2만 비교로
1회는 싸다. 기각 이유: (a) 배치마다 하면 마이크로벤치 기준 naive 집계 경로가
증분 경로의 **약 15배**(3,224.5us vs 215.9us/배치, PERF.md §2)로, 안 써도 되는 비용을
매초 60번 낸다. (b) 빈도를 낮추면(예: 500ms마다) 순위 신선도가 계단식이 된다.
(c) unstable sort의 동률 thrashing을 어차피 tiebreak로 풀어야 해서 "단순함"
이득이 생각보다 작다. RankIndex는 O(log n)/tick에 순위가 항상 정확하고,
등가성 테스트로 복잡도 리스크를 상쇄했다.

### 8-5. 시총/Top-20을 "필터된 집합 기준"으로 집계

검색 결과와 요약이 함께 움직이는 UX도 일리가 있다. 기각 이유: (a) 역할 정의 -
요약은 전체 시장 상황판으로 두는 쪽이 "2,000종목 관심목록" 화면의 목적에 맞고,
질의마다 시총 합계가 수십 경 단위로 널뛰는 표시는 오독을 부른다. (b) 비용 -
필터 기준 Top-20은 질의별 후보 구조 재구축(또는 순위 트리 2벌)이 필요해,
keystroke마다 O(n log n)급 작업이 생긴다. 전체 기준은 이 비용이 0이다.
채택 후 표시로 "(전체)"를 명시해 모호함을 없앴다. 필터 기준이 제품 요구로
확정되면: RankIndex에 필터 집합을 받는 view를 추가하는 확장 지점이 있다.

### 8-6. halted를 시총 합계/Top-20에서 제외

"정지 종목은 거래가 없으니 집계에서 빼자"는 직관. 기각 이유: (a) 시총 -
정지는 가격 발견의 중단이지 가치의 소멸이 아니다. 빼면 정지/해제 순간 합계가
그 종목 시총만큼 점프해, 지표가 시장이 아니라 정지 이벤트를 추적하게 된다.
(b) Top-20 - 정지 직전 상위권 종목이 증발하면 "왜 사라졌지"가 되고, 해제 때
갑자기 복귀하며 순위가 출렁인다. 동결 등락률로 포함 + "거래정지" 표기가 정보를
더 보존한다. (c) 일관성 - 포함 원칙으로 통일하면 두 집계에 별도 규칙이 없다
(§5). 제외를 택했다면 "시총은 포함하되 Top-20은 제외" 같은 비대칭의 논리를
추가로 방어해야 했다.

### 8-7. 시세 플래시/숫자 보간 등 모션 효과

트레이딩 UI 관행인 가격 변동 플래시(등락 시 행 배경을 잠깐 밝혔다 감쇠)를 검토하고
기각했다. 플래시는 **갱신 빈도를 통제할 수 있을 때만 성립하는 장치다** - 감쇠가
끝나기 전에 다음 갱신이 오면 강조가 아니라 뷰포트 전체의 스트로브가 된다. 이
feed의 보이는 행은 평균 270ms 간격으로 갱신되고(PERF.md §2) 관행적 감쇠는 300ms
안팎이라 정확히 그 조건에 걸린다. 성립시키려면 감쇠 시간을 조절할 것이 아니라
행당 갱신 빈도 자체를 낮춰야 하는데, 소비 계층에서 표시용으로 tick을 솎아내는
것은 신선도 요구와 정면 충돌한다. 성능 면에서도 "값이 바뀐 프레임만 그린다"를
"바뀐 후 일정 시간 계속 그린다"로 바꿔 §4 실측의 전제를 깬다.

숫자 보간(카운트업)도 기각했다. 기준: **데이터를 왜곡하지 않는 표현을 고른다.**
보간은 체결된 적 없는 중간 가격을 화면에 만들어내며, "매 프레임 표시값 == 스토어
최신값"이라는 신선도 계약(`freshness_test`가 고정)의 설계적 위반이다. 시세는 이산
사건이므로 즉시 교체가 정답이다. 스파크라인의 점-사이 직선 연결은 이와 다르다 -
존재하지 않는 값의 표시가 아니라 측정점 사이 시간 경과를 잇는 시계열 관례다.

배너/화면 전환 등 tick과 무관한 모션은 이 데모의 축 밖 폴리시로 §9와 같은 기준으로
생략했고, 모션이 없으므로 감속 모션 선호(reduce motion) 대응 대상도 공집합이다.

### (참고) 초성 검색 라이브러리 도입 - §5에서 기각, 사유 동일 원칙(§7).

## §9. 의도적 생략과 한계

- **테마는 다크 기본 + 앱바 토글로 라이트 전환**: 시세 화면은 어두운 배경에서
  등락색 대비가 좋아 국내 증권앱의 사실상 표준이라 다크를 기본으로 잡았다.
  색은 테마 토큰과 brightness 분기로 두어 전환이 자료구조/상태 계층과 무관하다.
  시스템 설정 연동과 반응형 폴리시는 이 데모의 축(설계/성능) 밖이라 하지 않았다.
- **시가/고가/저가는 세션 관측 기준** (§6): feed가 당일 이력을 제공하지 않는
  제약의 정직한 표기이며, 화면에 명시했다.
- **집계 통지 주기 분리 미구현** (§4 말미): 현 부하에서 실측상 불필요해
  구조(GatedNotifier)만 마련하고 손잡이는 만들지 않았다.
- **web 배포의 한계는 별도 문서에 정직하게**: SEO 사실상 0, 스크린리더
  시맨틱스는 DOM 기반 데모보다 약하다. 한계와 취한 조치는 README의 "웹에서의
  한계" 절에 있다.
- **접근성(스크린리더) 라벨 미작성**: 범위 판단. 특히 고빈도 시세 화면에 라이브
  리전을 순진하게 달면 갱신마다 낭독되어 소음이 된다 - 제대로 하려면 갱신 전달이
  아니라 주기 요약(throttle) 낭독이라는 별도 설계가 필요해서, 라벨만 붙이는
  시늉은 하지 않았다.

## §10. 요구가 바뀌면 어디를 고치는가

이 구조를 고른 이유의 절반은 "무엇을 안 고쳐도 되는가"에 있다. 예상되는 변경별로
수정 지점과 **손대지 않아도 되는 범위**를 미리 적어 둔다. 파라미터 변형 내성은
문서 주장이 아니라 테스트로 고정되어 있다 - `feed_variations_test.dart`가 종목 수
50/5,000, 배치당 1건, 지연 tick 25배, 정지 25배, 에러 p=0.3, 다른 seed의 9개 변형에서
불변식(가격 역행 없음, 집계 등가성, 구독 생존)을 검증한다.

| 변경 | 고치는 곳 | 그대로 두는 곳 | 비용 |
|---|---|---|---|
| 배치 빈도 10배 (600Hz) | `NOTIFY_MS` 스윕 재실행 후 값 선택 (빌드 플래그, 코드 무변경) | 상태/집계/검색/UI 전부 | 측정 1회 |
| 종목 20만 개 | notifier 지연 생성(보이는 행만), RankIndex에 상위 K 후보 구조 | 정합성/에러/검색 규약 | 중 |
| 시총/Top-20을 필터 집합 기준으로 (§8-5 기각안 채택) | RankIndex에 필터 view 추가, SummaryBar 라벨 | 스토어/행/에러 모델 | 소~중 |
| web 타깃 추가 | 시총 int 누적 -> BigInt 또는 주기적 재합산 검증 (§5의 네이티브 전제) | 나머지 전부 | 소 - **실제로 실행됨**: web 데모화 때 BigInt 전환에 파일 4곳/테스트 2곳 수정으로 끝났다 (§5) |
| 실제 WebSocket 연동 | `MarketRepository`만 (재연결/백오프/수신 큐) | 스토어 이하 전부 - 이미 "배치를 받을 뿐"이다 | 소 |
| 정지 종목을 집계에서 제외 (§8-6 기각안 채택) | 스토어의 시총 델타/rank 갱신에 상태 분기 | UI/검색 | 중 (일관성 논리를 새로 방어해야 함) |
| 등락률 외 정렬키 추가 (거래량 순 등) | RankIndex 인스턴스 추가 (rate 배열만 다름) | 스토어 적용 경로 | 소 |

경계를 이렇게 그은 대가도 분명하다. **스토어가 정합성/집계/통지 세 가지를 함께 쥐고
있어서** 위 표의 "중" 항목들은 대부분 이 파일 하나에 몰린다. 지금 크기에서는 한 곳에
모여 있는 편이 추적에 유리하다고 판단했고, 더 커지면 집계(시총/순위)를 스토어가 구독하는
별도 객체로 분리하는 것이 다음 수순이다 - 통지가 이미 `GatedNotifier`로 분리되어 있어
그 분해는 기계적이다.

## §11. 테스트 전략 - 무엇을 왜 골랐나

**선정 기준: "틀려도 조용한 것"을 먼저 덮는다.** 이 화면에서 깨지면 눈에 띄는 것(목록이
안 뜬다)은 실행 한 번으로 잡히지만, 지연 tick 한 건이 가격을 되돌리거나 동률 순위가
흔들리는 것은 화면을 오래 봐도 모른다. 그래서 회귀 테스트는 **명세가 함정으로 지목한
엣지**에 집중했다: 역순/동일 timestamp 기각, 3단 상태 전이, 정지 직전 지연 tick,
값 불변 tick, 에러 생존/복구, 동률 tiebreak.

**오라클은 브루트포스로 둔다.** 증분 유지 자료구조는 "결과가 그럴듯한데 틀린" 실패를
하므로, 기대값을 손으로 적지 않고 **전량 재계산과 대조**한다 - 증분 시총 - 전체 재합산,
RankIndex - 문자열 비교 전체 정렬(`rank_index_test.dart`는 코드 배열이 사전순이 아닌
경우와 무작위 3,000회 갱신 fuzz까지 포함한다). 실제 feed 수열을 그대로 흘려 넣어
대조하므로, 사람이 상상하지 못한 조합도 검사 범위에 들어온다.

**시간과 무작위성은 주입으로 제거한다.** feed는 seed 고정 + `pump()`, 복구 히스테리시스는
`nowMs` 주입, 검색 debounce는 주입한 `Duration`으로 제어한다. 벽시계에 남겨둔 것은
debounce 동작 자체를 확인하는 테스트 하나뿐이고(50ms 설정에 80ms 대기), 나머지는
가상 시간이라 CI에서 흔들리지 않는다.

**성능도 회귀 테스트를 붙였다.** `micro_bench_test`(증분 < 전량 재계산),
`throughput_test`(상한 부하 15,000건/s에서 배치당 비용 < 프레임 예산의 1/4),
`rank_cost_test`(순위 유지가 적용 비용의 최대 항목)는 수치를
출력하면서 예산을 벗어나면 실패한다. 설계 의도가 코드에서 조용히 사라지는 것을 막는 장치다.
신선도 요구도 자동 증명이다 - `freshness_test`는 실제 실행 경로(`start()`의 60Hz
타이머)로 구동하며, 매 프레임 보이는 행의 표시 가격이 스토어 최신값과 일치함을
드래그 제스처 중까지 포함해 단언한다. 이것이 참이면 stale은 항상 1프레임 이하다.
`soak_test`(200초 분량)는 tick 회계 일치와 자료구조 상수성을 장시간 구간에서 고정한다.

**의도적으로 안 한 것**: 골든 이미지 테스트(레이아웃은 이 데모의 축이 아니고 유지비만 큼),
커버리지 목표치(엣지 6종을 덮었는지가 숫자보다 중요), 실기기 매트릭스(측정 환경은
PERF.md §7에 한계로 명시), 상세 화면의 스파크라인 픽셀 검증(repaint 트리거 조건은
위젯 테스트로, 그림 자체는 육안으로).
