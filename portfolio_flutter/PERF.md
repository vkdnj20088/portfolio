# PERF.md - 병목 분석과 before/after 실측

> 모든 프레임 수치는 **profile 모드**에서 측정했다 (debug는 JIT/assert 비용으로
> 실제보다 훨씬 느리다 - 일반적인 Flutter 성능 측정 관례). 재현 커맨드는 §1, 결과는 §4.
> 설계 결정의 배경과 근거는 [DESIGN.md](DESIGN.md), 여기서는 수치와 그 해석만 다룬다.

## §0. 이 수치는 언제, 어떤 트리에서 측정한 것인가

**2026-08-10, 지금 저장소의 코드 그대로 측정했다.** 데이터 소스(`lib/feed/`)와 BigInt
시총 누적을 포함한 현재 상태이고, 문서에 남은 수치 중 다른 트리에서 온 것은 없다.

이번 세션에서 **측정 방법을 두 군데 바꿨다.** 이전 수치와 절대값을 직접 비교하면 안 되는
이유다.

1. **창 전면 유지 방식** - 이전에는 주기적으로 창을 재활성화했는데, 그 재활성화 자체가
   외부 스톨을 만드는 것으로 의심됐다(개선본 `idle15k`에서 p99 49.5ms / worst 96.9ms의
   스파이크 6프레임). 이번에는 **전면이 아닐 때만** 활성화하도록 바꿨고, 그 구간의
   스파이크가 사라졌다(p99 9.45ms, worst 9.58ms, jank 0%). 의심과 일치하는 결과지만
   단일 변인 실험은 아니다 - 세션도 입력 수열도 함께 달라졌다.
2. **§2 분해와 §6-3 대조의 하네스** - 저장소 밖 일회성 하네스에서 재던 것을
   [test/rank_cost_test.dart](test/rank_cost_test.dart)로 옮겨 누구나 재현할 수 있게 했다.
   측정 방식이 달라져 값도 달라졌다(순위 유지 비중이 83% -> 약 71%). 옛 하네스는 공통
   루프 위에 항목을 하나씩 얹어 빼는 방식이었고, 지금은 **실제 `applyBatch` 총시간** 대
   **그 배치가 실제로 일으킨 갱신열을 실제 `RankIndex`에 먹인 시간**의 비다. 항목별
   6분할은 유지하지 않는다 - 각 항목을 재구현해야 하고, 그러면 "재구현이 원본과 같은가"
   라는 더 나쁜 불확실성이 들어온다.

## §1. 측정 방법 - 재현 가능성

### 결정론적 입력

`MarketFeed`를 `start()` 대신 **`pump()`** 로 구동한다. 기본 seed
고정이므로 baseline/개선본/스윕 구성이 **바이트 단위로 동일한 tick 수열**
(지연/역순 tick, 거래정지 포함)을 받는다. 시나리오는
[integration_test/perf_test.dart](integration_test/perf_test.dart) 하나이며,
앱 부팅 시 repository가 구독을 걸어둔 뒤 pump하므로 "리스너가 붙어야 방출"
조건을 항상 만족한다.

### 시나리오 (5구간, 워밍업 60배치는 측정 제외)

| 구간 | 내용 | 부하 성격 |
|---|---|---|
| `idle` | 정지 화면에 200배치(약 3.3초 분량) 주입 | 순수 tick 반영/집계 비용 |
| `scroll` | fling 12회 x 각 16배치 주입 | 스크롤(행 mount/unmount) + tick 동시 |
| `idle15k` | 프레임당 배치 2개 x 200프레임 (약 초당 14,850건) | feed 상한 부하 (§6-2) |
| `search` | `ㅎㅂ` 필터 적용 상태로 200배치 (한빛* 그룹 = 전체의 1/16) | 필터 상태에서의 tick 반영 |
| `detail` | 상세 화면을 띄운 채 150배치 (개선본 전용 - baseline은 상세 없음) | 구독 수명 관리 효과 |

### 지표

엔진 `FrameTiming` 콜백에서 구간별로 수집:
- **build**: UI 스레드 프레임 구성 시간 (avg / p50 / p90 / p99 / worst, ms)
- **raster**: 래스터 스레드 시간 (avg / p90 / worst, ms)
- **jank**: build 또는 raster가 16.7ms(60fps 예산)를 넘은 프레임 수/비율

### 재현 커맨드

```bash
# baseline -> 개선본 -> 통지 주기 스윕 순서로 5회
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/perf_test.dart -d macos --profile \
  --dart-define=BASELINE=true          # baseline
# (define 없이)                        # 개선본, 통지 주기 0ms
# --dart-define=NOTIFY_MS=50|100|200   # 스윕

# §2/§6-1/§6-3의 CPU 수치 (debug JIT - 상대 비교용)
flutter test test/micro_bench_test.dart test/rank_cost_test.dart \
             test/throughput_test.dart test/soak_test.dart
```

각 실행이 stdout에 `PERF_SUMMARY {...}`(구간별 지표)와 `STORE_STATS {...}`를
남긴다. §4의 표는 이 라인들을 그대로 옮긴 것이다.

**측정 중 지켜야 할 조건 둘** - 어느 하나만 어겨도 수치가 앱 비용이 아니라 환경 잡음이 된다.

1. **벤치 창을 전면에 유지한다.** 가려지면 macOS가 Metal drawable 공급을 지연시켜
   raster 스레드가 수백 ms 단위로 블록된다. 다만 **주기적으로 재활성화하지는 않는다** -
   그 재활성화가 스톨을 만든다(§0). 전면 여부를 읽어 **아닐 때만** 활성화하면 된다.
2. **같은 기계에서 다른 작업을 겹치지 않는다.** 이번 1차 실행에서 `NOTIFY_MS=100/200`
   구간에 의존성 설치/테스트/타입체크를 겹쳐 돌렸고, 그 두 구성에만 raster worst
   25.7ms / 34.8ms 가 찍혔다. 다른 작업 없이 재실행하니 각각 1.6ms / 1.9ms 로 내려갔다.
   §4-2 표의 100/200 행은 재실행 값이다.

### 측정 환경

macOS 15.7.8 / Intel Core i7-9750H(6C12T) / 16GB / Flutter 3.44.9(stable) /
Dart 3.12.2 / macOS desktop 타깃, profile 모드. 열 스로틀링이 있는 노트북이므로
절대값보다 **동일 조건 상대 비교**가 의미의 중심이다. 세션이 다르면 입력 수열도
기계 상태도 달라지므로, **다른 세션의 절대값끼리 빼서 해석하지 않는다.**

## §2. 부하 특성 분석 - 병목은 연산이 아니라 rebuild 전파

최적화 전에 부하의 자릿수부터 계산했다. feed 파라미터(60Hz, 배치당 1~250건)에서:

| 항목 | 값 | 계산 |
|---|---|---|
| 평균 tick 유입 | **~7,400건/s** (최대 15,000) | 60Hz x 평균 123.7건 - 실측 600배치에 74,193건(=123.7/배치) |
| 종목당 tick 간격 | 평균 **~270ms** | 7,420 / 2,000종목 = 약 3.7건/s/종목 |
| 화면에 보이는 행 | ~15행 (56px x ~800px 뷰포트) | 보이는-행 갱신은 약 15 x 3.7 = **초당 56건, 프레임당 약 1건** |
| 배치 1개 적용 비용 (본 구현) | **215.9us** (debug JIT; profile은 그 이하) | 마이크로벤치, 아래 |
| 프레임 예산 대비 | 16.7ms의 **~1.3%** | 215.9us / 16.7ms |

마이크로벤치 (`flutter test test/micro_bench_test.dart`, 동일 캡처 배치 600개를
두 소비자에 주입 - debug JIT이므로 **상대 비교용**). 단독 실행 4회의 대표값이며
범위는 store 212.5~231.6 / naive 3,076~3,225us다:

```
MICRO_BENCH ticks=74193 batches=600
  store_us_per_batch=215.9      # 본 구현: 정합성 검증+3단 상태+증분 시총+RankIndex 전부 포함
  naiveagg_us_per_batch=3224.5  # 배치마다 시총 전량 재합산 + 2,000건 전체 정렬
  stats=ApplyStats(applied: 74125, rejectedStale: 34, unchanged: 34)
```

### 적용 비용의 내부 분해 - 지배 항목은 하나다

전체가 예산의 1~2%라는 것만 알면 어디를 고칠지는 알 수 없다. 같은 입력으로 순위 유지 비용을
따로 재봤다 (`flutter test test/rank_cost_test.dart`). 재는 방식은 이렇다: 실제
`applyBatch`로 600배치를 흘려 총시간을 재고, **같은 배치가 `RankIndex`에 실제로 일으킨
갱신열 59,177회**를 뽑아 실제 `RankIndex`에 그대로 먹여 그 시간을 잰다. 갱신열 추출은
스토어가 순위를 갱신하는 조건 둘(timestamp 단조 통과 + 가격 변화)만 옮긴 것이다.
양쪽 모두 워밍업 1회 뒤 4회 중 최소값이다.

| 구성요소 | 비용 | 비중 |
|---|---|---|
| **순위 유지 (SplayTreeSet 제거+삽입)** | 55.2ms | **71%** |
| 나머지 전부 (맵 조회/timestamp 검증/Quote 할당/비교/시총 델타/통지/top20) | 22.6ms | 29% |
| **applyBatch 전체** | **77.8ms** | 129.6us/배치, **1.05us/tick** |

(비중의 4회 실행 범위는 69.1~74.0%다. 전체값이 위 마이크로벤치보다 낮은 것은 이 표가
워밍업 후 최소값이고 마이크로벤치는 단일 실행이기 때문이다.)

**순위 유지가 적용 비용의 약 70%**이고, 나머지 전부를 0으로 만들어도 30% 남짓밖에
줄지 않는다. 최적화 손잡이는 사실상 하나다(§6-3). 이 비중은 측정 방법을 바꿔도
유지된다 - 옛 하네스 83%, 지금 하네스 71%로 값은 달라졌지만 지배 항목이 하나라는
결론은 같다.

**결론(가설)**: 순수 연산은 증분 유지 시 프레임 예산의 1~2%로, 병목일 수 없다.
전량 재계산 경로조차 배치당 3.2ms(debug)다. 그렇다면 baseline이 느린 이유는
연산이 아니라 **(1) 배치마다 화면 전체를 rebuild 대상으로 만드는 setState 전파,
(2) 그 build 안에서 다시 하는 전량 재계산, (3) RepaintBoundary 부재로 인한 넓은
repaint**여야 한다. 이 가설이 맞다면 "전파를 차단"한 개선본은 연산을 더 빠르게
만들지 않고도 프레임을 회복해야 한다 - §4가 이를 검증한다.

## §3. baseline -> 개선본: 무엇을 바꿨고 왜 그 항목인가

baseline([lib/baseline/baseline_page.dart](lib/baseline/baseline_page.dart))은
비교 기준의 정의 그대로다: 배치마다 `setState()` 전체 rebuild, 매 build 시총
전량 재합산/Top-20 전체 정렬/검색 전량 재스캔(초성 재추출 포함), 행에
RepaintBoundary/itemExtent 없음, timestamp 검증 없음, tiebreak 없음.

| # | 개선 항목 | 대체한 baseline 동작 | 겨냥한 병목 |
|---|---|---|---|
| 1 | 종목별 `ValueListenable` 구독 (행당 1구독) | 페이지 전체 setState | 배치당 rebuild 범위: 화면 전체 -> 값이 바뀐 보이는 행만 |
| 2 | 행 `RepaintBoundary` + `itemExtent` 고정 | 경계 없음 | 행 1개 텍스트 변경이 목록 레이어 전체를 다시 그리는 것 차단, 스크롤 layout 상수화 |
| 3 | 시총 합계 정수 델타 누적 | 매 build 2,000건 재합산 | build 경로에서 O(n) 제거 (+부동소수 오차 원천 제거) |
| 4 | `RankIndex` (SplayTreeSet, O(log n)/tick) | 매 build 2,000건 정렬 | build 경로에서 O(n log n) 제거, 동률 tiebreak로 rank thrashing 제거 |
| 5 | Top-20 통지를 "순서 변경 시만" | 매 배치 스트립 rebuild | 순위 불변 프레임의 스트립 build 0회화 |
| 6 | 검색 정적 인덱스 + debounce 120ms | 매 build 전량 매칭(초성 재추출) | 필터 비용을 tick 경로에서 완전 분리 (질의 변경 시에만) |
| 7 | 상세 진입 시 통지 범위 제한 | (baseline 상세 없음) | 상세 화면 동안 목록 rebuild 비용 0 |
| 8 | 값 불변 tick 통지 생략 | 무조건 setState | halted 반복/clamp 고착 tick의 무의미한 rebuild 제거 |

정합성 장치(timestamp 기각/3단 상태/에러 복구)는 성능 항목이 아니지만 **같은
경로 위에** 있다 - §2의 215.9us는 이들을 전부 포함한 비용이다. 즉 "정합성을
지키느라 성능을 냈다"가 아니라, 정합성 포함 적용 비용 자체가 예산의 1%대다.

## §4. 결과 - before/after 실측

> 아래 수치는 §1 커맨드의 출력(`PERF_SUMMARY` 라인)을 그대로 옮긴 것이다.
> 단위: ms. jank = build 또는 raster > 16.7ms인 프레임.

### 4-1. baseline vs 개선본 (통지 주기 0ms)

| 구간 | 구성 | 프레임 | build avg | p50 | p90 | p99 | worst | raster avg | raster p90 | raster worst | jank% |
|---|---|---|---|---|---|---|---|---|---|---|---|
| idle | baseline | 202 | **7.26** | 7.24 | 9.80 | 12.08 | 12.18 | 0.85 | 0.96 | 1.72 | 0.0 |
| idle | **개선** | 274 | **2.27** | 1.59 | 5.48 | 8.79 | 10.15 | 1.05 | 1.39 | 1.56 | 0.0 |
| scroll | baseline | 864 | 2.61 | 1.14 | **8.56** | 11.96 | 13.92 | 1.04 | 1.32 | 1.80 | 0.0 |
| scroll | **개선** | 866 | 1.74 | 1.24 | **4.03** | 8.61 | 10.07 | 1.02 | 1.31 | 1.54 | 0.0 |
| idle15k | baseline | 203 | **8.33** | 8.44 | 10.07 | 11.92 | 13.62 | 0.84 | 0.94 | 1.43 | 0.0 |
| idle15k | **개선** | 210 | **3.65** | 3.58 | 6.36 | 9.45 | 9.58 | 0.93 | 1.13 | 1.47 | 0.0 |
| search | baseline | 222 | **7.19** | 7.59 | 9.62 | 12.45 | 16.21 | 1.82 | 1.29 | 196.50 | 0.45 |
| search | **개선** | 212 | **2.49** | 2.20 | 5.27 | 7.34 | 8.32 | 1.06 | 1.29 | 2.70 | 0.0 |
| detail | **개선** | 225 | **0.69** | 0.33 | 1.17 | 11.25 | 14.66 | 3.57 | 1.59 | 189.26 | 3.11 |

**build(UI 스레드) - 이번 최적화가 겨냥한 지표:**

- **idle: 7.26 -> 2.27ms (-69%).** baseline은 배치마다 전체 rebuild + 전량
  재계산으로 프레임 예산(16.7ms)의 43%를 상시 소모한다. 개선본은 14%.
  이 데스크톱(i7)에서는 둘 다 대체로 60fps가 나오지만, 모바일 AP에서는 이
  5.0ms 차이가 그대로 jank 마진이다 - 그리고 baseline은 이 비용을 **화면이
  조용해도** 낸다.
- **scroll: p90 8.56 -> 4.03ms (-53%).** 행 mount/unmount가 겹치는 구간에서
  꼬리가 절반 이하로 줄었다 (itemExtent 고정 + 행 단위 구독의 효과).
- **idle15k(유입 2배): avg 8.33 -> 3.65ms (-56%), p50 8.44 -> 3.58ms (-58%).**
  상한 부하에서도 개선본이 평상시 baseline(7.26ms)의 절반이다. 부하를 2배로
  올렸을 때 두 구성이 서로 다르게 반응하는 구조는 §6-2에서 따로 다룬다.
- **search: avg 7.19 -> 2.49ms (-65%).** baseline은 매 build 전량 매칭(초성
  재추출 포함)을 하고, 개선본은 정적 인덱스라 필터가 tick 경로에 비용을 얹지
  않는다.
- **detail: build avg 0.69ms.** 상세 화면이 떠 있는 동안 목록 통지를 정지한
  효과로, idle(2.27ms) 대비 -70% - "화면 뒤 목록의 갱신 비용이 유지되지
  않아야 한다"는 요구의 실측 증거다. p50은 0.33ms로, 프레임 대부분이 사실상
  아무 일도 하지 않는다.

**개선본은 다섯 구간 중 네 곳에서 jank 0%다.** 남은 하나(detail 3.11%)와 baseline
search(0.45%)는 성격이 같다: raster worst 189.3ms / 196.5ms 단발 프레임인데, 둘 다
화면 전환/필터 적용 순간의 drawable 재획득으로 재현마다 위치가 다른 **측정 환경
잡음**이다. build 쪽은 그 구간에서 평온하다(detail p90 1.17ms). 이번 세션에서는
이전에 개선본 `idle15k`를 덮었던 build 스파이크(p99 49.5 / worst 96.9ms)가 나오지
않았고, 그 자리는 p99 9.45 / worst 9.58ms로 예산 안이다(§0의 창 활성화 방식 변경).

**raster는 양쪽 구성 모두 평균 0.8~1.8ms로 예산에 한참 못 미친다** - 행 단위
RepaintBoundary의 효과로, 값이 바뀐 행의 텍스트 레이어만 다시 그린다.

### 4-2. 통지 주기 스윕 - 성능-신선도의 선을 실측으로 긋기

`NOTIFY_MS = 0 / 50 / 100 / 200` (0 = 배치 도착 즉시 통지). 신선도 상한은
"주기 + 1프레임"이므로 200ms 구성은 요구(<=200ms)를 정의상 초과한다.

| notifyMs | 구간 | build avg | p90 | p99 | worst | 신선도 상한 |
|---|---|---|---|---|---|---|
| **0 (채택)** | idle | 2.27 | 5.48 | **8.79** | 10.15 | **약 16ms** |
| 50 | idle | 1.61 | 6.84 | 8.97 | 10.83 | 약 66ms |
| 100 | idle | 1.19 | 5.09 | 10.50 | 12.59 | 약 116ms |
| 200 | idle | 0.87 | 0.36 | **11.57** | 13.03 | 약 216ms - **요구 위반** |
| **0 (채택)** | scroll | 1.74 | 4.03 | 8.61 | 10.07 | 약 16ms |
| 50 | scroll | 1.59 | 2.74 | 9.38 | 13.63 | 약 66ms |
| 100 | scroll | 1.41 | 2.66 | 10.05 | 12.56 | 약 116ms |
| 200 | scroll | 1.39 | 2.61 | 9.65 | 14.13 | 약 216ms - 요구 위반 |
| **0 (채택)** | idle15k | 3.65 | 6.36 | **9.45** | 9.58 | **약 16ms** |
| 50 | idle15k | 2.33 | 8.28 | 10.97 | 12.39 | 약 66ms |
| 100 | idle15k | 1.80 | 9.61 | 12.40 | 13.10 | 약 116ms |
| 200 | idle15k | 1.13 | 0.38 | **14.07** | 14.48 | 약 216ms - 요구 위반 |
| **0 (채택)** | search | 2.49 | 5.27 | **7.34** | 8.32 | **약 16ms** |
| 50 | search | 1.81 | 5.82 | 9.09 | 10.60 | 약 66ms |
| 100 | search | 1.61 | 6.89 | 11.23 | 17.67 | 약 116ms |
| 200 | search | 1.18 | 1.17 | **13.22** | 15.30 | 약 216ms - 요구 위반 |

읽는 법 - 주기를 키우면 **build 평균은 내려간다**(idle 2.27->0.87, idle15k
3.65->1.13: 60Hz 요약/Top-20 rebuild가 모이는 효과). 반면 **꼬리는 정확히 반대로
움직인다.** 이번 세션은 잡음이 걷혀서 그 방향이 단조로 보인다 - p99가 idle
8.79->8.97->10.50->11.57, idle15k 9.45->10.97->12.40->14.07, search
7.34->9.09->11.23->13.22 로 네 구성에 걸쳐 계속 나빠진다(scroll만 200ms에서 살짝
꺾인다). 한 번의 flush에 여러 배치 분량의 통지가 몰리기 때문이고, worst도 같은
방향이다(search 8.32 -> 15.30ms).

즉 **주기를 키워서 사는 것은 평균이고, 파는 것은 신선도(최대 12배)와 꼬리
예측 가능성**이다. 어느 구성도 평상시 프레임 예산을 위협하지 않는 상황에서
신선도가 가장 좋고 꼬리도 가장 짧은 **0ms를 채택**했다 - DESIGN.md §4의
"즉시 통지 = 프레임 정렬 coalescing" 논지의 실측 근거다.

단, 스윕은 다음 손잡이가 어디인지도 보여준다: 요약 영역이 지금보다 무거워져
build 평균을 낮춰야 하는 날이 오면, 첫 수단은 `NOTIFY_MS=50`이다 (idle15k avg
-36%, 신선도 상한 66ms로 여전히 요구의 1/3). 이 판단이 코드 변경 없이 빌드
플래그로 가능하도록 남겨두었다.

(detail 구간은 채택 구성에서만 잰다. 통지 주기를 키우면 상세 화면에서 프레임
자체가 희소해져 표본이 드로어블 대기 아티팩트로 뒤덮이고, 애초에 이 구간은 통지 주기가
아니라 구독 수명 관리의 효과를 보는 자리라 스윕 비교 대상이 아니다.)

## §5. 스토어 통계 - 정합성 장치의 실측 개입률

시나리오 전체(워밍업 포함, idle15k 때문에 배치 수가 구간별로 다르다)의 `STORE_STATS`:

| 구성 | 측정 구간 | applied | rejectedStale (역순 기각) | unchanged (값 불변) |
|---|---|---|---|---|
| NOTIFY_MS = 0 | idle15k + search + **detail** | 149,704 | 66 | 57 |
| NOTIFY_MS = 50 | idle15k + search | 130,357 | 60 | 49 |
| NOTIFY_MS = 100 | idle15k + search | 130,357 | 60 | 49 |
| NOTIFY_MS = 200 | idle15k + search | 130,357 | 60 | 49 |

- **역순 tick 기각률 0.044%** (66/149,770): 지연 tick은 드물지만 실재하며,
  기각하지 않으면 그 66번마다 가격/거래량이 과거로 튀는 화면이 된다.
  버리는 정보량은 무시 가능한 수준 - "timestamp 단조 강제" 정책의 비용이
  사실상 0임을 뜻한다.
- **값 불변 tick 57건**: 통지/집계를 모두 건너뛴 건수. 처음에는 "clamp(±30%)
  고착이 누적되는 장시간 세션일수록 커질 것"으로 예상했으나, 200초 분량 soak
  실측(`soak_test.dart`, 149만 tick)이 이를 **반증**했다 - 완전 불변은 전/후반
  372 vs 243건으로 늘기는커녕 줄었다(전체의 0.04%). 가격이 고착되어도 거래량은
  계속 변하기 때문에, clamp 고착은 완전 불변이 아니라 **"가격 고착 + 거래량 변동"
  버킷에 쌓인다: 295,602건, 전체 tick의 ~20%**다. 이 20%가 필드별 변경 플래그
  (§3-8)의 실측 근거다 - 행 통지만 하고 시총 델타/순위 갱신을 건너뛰므로,
  전체 tick의 1/5에서 rank 갱신(적용 비용의 약 70%, §2)이 사라진다.
- **통지 주기가 다른 세 구성의 통계가 완전히 동일**하다는 것이 이 표의 핵심
  결론이다: 같은 입력(seed 고정)에 대해 상태 계층의 결과가 **통지 정책과 무관**하게
  바이트 단위로 같다 - "정합성은 도착 즉시, 화면 전파만 제어"(DESIGN.md §1)
  라는 분리 불변식이 측정으로 검증된 셈이다. 성능 튜닝(통지 주기)이 정합성을
  건드릴 수 없는 구조라는 뜻이기도 하다.

## §6. 부하 상한(15,000건/s)에서의 여력

feed 의 전제는 "초당 최대 약 15,000건"인데, **seed가 실제로 내는 평균은 그 절반이다.**
배치 크기가 `1 + Random.nextInt(250)`(1~250 균등)이라 평균 123.7건 x 60Hz = 약 7,400건/s이고,
15,000건/s는 배치가 상한 근처를 뽑은 프레임에서만 순간적으로 스친다. §4의 수치는 그
"평균 7.4k/s + 상한 스파이크" 부하에서의 측정이므로, 상한이 **지속**될 때의 여력은
따로 재야 한다. 두 갈래로 쟀다.

### 6-1. 합성 상한 부하 - 상태 계층 단독 (재현 5초)

[test/throughput_test.dart](test/throughput_test.dart): 250건짜리 배치 600개
(= 60Hz 기준 10초 분량, 총 150,000 tick)를 스토어에 직접 주입한다. **이 배치는 seed가
만든 수열이 아니라 합성 부하다** - seed는 읽기만 하고 수정하지 않되, 상한값을 지속시키려면
tick을 직접 만드는 수밖에 없기 때문이다. 화면에 뜨는 행 수만큼(20개) 리스너를 붙인다.

```
THROUGHPUT_15K ticks=150000 batches=600 total_ms=254
  us_per_batch=424.2   ns_per_tick=1697   cpu_pct_of_one_core=2.55
```

단독 실행 4회 범위는 412.5~435.0us/배치, 한 코어의 **2.47~2.61%**다 (60Hz에서는
"배치당 비용 / 프레임 예산"과 "CPU 점유율"이 같은 값이 된다). debug(JIT) 값이므로
profile에서는 이보다 낮다 - 즉 이 수치는 **상한선**이다.
같은 테스트가 배치당 비용이 프레임 예산의 1/4을 넘으면 실패하는 회귀 가드를 겸한다.

"여유롭다"는 어디서 깨지는지 알 때만 의미가 있어서, 유입을 계속 올리는 스윕도
같은 파일에 있다 (`SCALE_SWEEP`): 프레임당 125/250/500/1,000/2,000건
(7.4k~120k건/s 상당)에서 배치당 130~144 / 360~390 / 640~760 / 653~770 / 772~848us
(4회 범위). 배치가 커질수록 tick당 단가가 내려가고(고착 가격의 재갱신 비율 증가),
**이 유니버스의 물리적 최대 유입 - 전 종목이 매 프레임 갱신되는 120k건/s - 에서도
프레임 예산의 5%다.** 상태 계층의 포화점에는 배치 크기로는 도달할 수 없다는 뜻이고,
그래서 스케일 한계는 유입이 아니라 종목 수 축에 있다 (DESIGN.md §10의 "종목 20만 개" 행).

### 6-2. 진짜 seed 수열로 상한 재현 - 프레임 레벨

합성 부하는 tick의 성질(지연/역순, 정지)이 빠진다. 그래서 벤치에 `idle15k` 구간을 두어
**프레임당 배치를 2개씩** 밀어 넣는다: 123.7건 x 2 x 60프레임 = 약 **초당 14,850건**이,
seed가 만든 진짜 수열 그대로 들어온다. seed는 손대지 않는다 - 소비 쪽에서 `pump(2)`를
부를 뿐이다.

> 단서: feed 내부 시계는 배치당 +16ms이므로 이 구간은 **가상 시간이 2배로 흐른다**
> (벽시계 1초 = feed 기준 2초). 부하 재현이 목적이며, 신선도 예산은 벽시계 기준
> 그대로다.

| 구성 | 유입 | build avg | p50 | p90 | p99 | worst |
|---|---|---|---|---|---|---|
| baseline | 7.4k/s (`idle`) | 7.26 | 7.24 | 9.80 | 12.08 | 12.18 |
| baseline | **14.9k/s (`idle15k`)** | 8.33 | 8.44 | 10.07 | 11.92 | 13.62 |
| 개선 | 7.4k/s (`idle`) | 2.27 | 1.59 | 5.48 | 8.79 | 10.15 |
| 개선 | **14.9k/s (`idle15k`)** | **3.65** | **3.58** | 6.36 | 9.45 | 9.58 |

상한 부하에서도 개선본의 build는 p50 3.58ms(예산의 21%), p90 6.36ms로 예산 안이다.
두 구성의 반응 차이가 구조를 드러낸다 - baseline은 부하가 2배가 되어도
7.26 -> 8.33ms(+15%)로 크게 움직이지 않는다. tick 수와 무관하게 매 프레임
화면 전체를 다시 만들기 때문에 이미 비용의 천장에 붙어 있는 것이다. 개선본은
p50 기준 1.59 -> 3.58ms로 부하에 비례해 늘어난다. 실제로 바뀐 것만 갱신하니
당연하고, 그럼에도 **상한 부하의 개선본이 평상시 baseline(7.26ms)의 절반이다.**

### 6-3. 그래서 어디를 고쳤나 - RankIndex tiebreak

§2의 분해가 손잡이를 하나로 특정했다: **순위 유지가 적용 비용의 약 70%**. 그 안에서
비교자는 갱신 1회당 O(log n)회 호출되는 가장 뜨거운 코드였고, 거기서 종목코드
**문자열 비교**를 하고 있었다. 이것을 생성 시 1회 계산한 **정수 순위**로 바꿨다
(등락률도 `compareTo` 대신 원시 비교). 순서 규약은 그대로다.

측정 -> 변경 -> 재측정 순으로, 같은 갱신열(가격이 실제로 바뀐 59,177건)을 두 구현에
교차로 먹여 비교했다. 구 구현은 [test/rank_cost_test.dart](test/rank_cost_test.dart)에
원형 그대로 복제해 두어 언제든 다시 잴 수 있다:

| | 갱신 1회 | 갱신열 전체(59,177회) |
|---|---|---|
| 문자열 tiebreak (before) | 1,299ns | 76.9ms |
| **정수 tiebreak (after)** | **933ns** | **55.2ms** |
| 차이 | **-28.2%** | -28.2% |

(4회 실행 범위 -23.1~-30.2%.) 순위 유지가 적용 비용의 약 70%이므로 적용 경로
전체로는 약 -20%에 해당한다.

동치성은 눈으로 확인할 성질이 아니라서 테스트로 못박았다
([test/rank_index_test.dart](test/rank_index_test.dart)): 코드 배열이 사전순으로 들어오지
않는 경우(정수 tiebreak가 index가 아니라 코드 순위를 따라야 한다)와 동률이 대량 발생하는
무작위 3,000회 갱신 fuzz를, 매번 **문자열 비교 전체 정렬**과 대조한다. 위 대조 하네스도
매 실행 두 구현의 Top-20이 같은지 확인한다.

**그럼에도 이 최적화는 현 부하에서 불필요한 여력이다.** 상한 부하 기준 한 코어 2.5%
언저리에서 그 일부를 덜어내는 것은 프레임을 하나도 더 살리지 못한다 - §4의 어떤
구간에서도 이 차이는 측정 노이즈에 묻힌다.
반영한 이유는 다른 데 있다: 비용이 **생성 시 O(n log n) 한 번 + 정수 배열 하나**로 끝나고,
지배 항목이 하나로 특정된 상태에서 그 항목의 상수를 줄여 두는 것이 종목 수가 늘 때 남는
유일한 여유이기 때문이다. 반대로 **채택하지 않은 것**은 상위 K 후보 구조다 - 순위 정확성을
전순서로 보장하는 현재 성질을 잃고 등가성 테스트가 성립하지 않게 되는데, 그 대가를
2%짜리 문제에 지불할 이유가 없다 (DESIGN.md §10의 "종목 20만 개" 행에 재검토 조건으로 남겼다).

### 6-4. 남은 손잡이

분해표 기준으로 순위 유지를 제외한 전부(통지/할당/시총/조회)를 0으로 만들어도 약 30%다.
다음 실질적 손잡이는 순서대로 (1) 상위 K 후보 구조로 트리 크기 축소, (2) 집계 통지 주기
분리(§4 말미), (3) 파생 계산이 무거워질 경우의 isolate 오프로딩(DESIGN.md §8-3)이며,
셋 다 **현 부하에서는 근거가 없다.** 근거가 생기는 조건은 각 항목에 적어 두었다.

## §7. 한계와, 더 쟀다면

- **단일 머신/단일 실행**: 프레임 수치는 구성당 1회 실행이다. run-to-run 편차(열
  스로틀링, OS 스케줄링)를 통계 처리(N회 반복/신뢰구간)하지 않았다. 구성 간 격차가
  자릿수 수준이라 결론이 뒤집힐 여지는 작다고 판단했고, CPU 수치(§2/§6-1/§6-3)는
  4회 실행의 범위를 함께 적었다. 반복 실행 스크립트는 §1 커맨드로 대체된다.
- **측정 환경이 수치를 만든다**: 이번 세션이 그 실례다. 창 활성화 방식 하나로 개선본
  `idle15k`의 worst가 96.9ms에서 9.58ms로 바뀌었고, 같은 기계에서 다른 작업을 겹친
  두 구성만 raster worst가 25~35ms로 튀었다(§1의 조건 둘). 앱을 고치지 않고도 이만큼
  움직이므로, **다른 세션의 절대값끼리 비교하지 않는다.**
- **macOS 데스크톱 측정**: 모바일 GPU/스레드 모델과 raster 특성이 다르다.
  기기 실측이 필요하면 같은 커맨드에 `-d <기기>`만 바꾸면 된다 (시나리오/seed
  동일). iOS 시뮬레이터는 raster 경로가 달라 성능 측정에 쓰지 않았다.
- **web 타깃은 프레임을 재지 않았다**: 배포는 `flutter build web --wasm` 산출물인데,
  이 문서의 프레임 수치는 전부 macOS desktop profile이다. WasmGC/skwasm의 raster
  경로가 달라 그대로 옮겨 읽을 수 없다. web 에서 잰 것은 첫 로드 전송량뿐이고
  ([README.md](README.md)), 프레임은 재지 않았다.
- **가상 키보드/IME 미개입**: `enterText`는 IME 조합 비용을 우회한다. 초성
  검색의 실사용 타이핑 부하는 debounce(120ms)가 흡수하므로 결론에 영향이
  없다고 판단했다.
- **메모리 프로파일 생략**: 고정 자료구조(notifier 2,000개, 링버퍼 180) 중심이라
  누수 위험이 낮다고 보고 프레임에 시간을 썼다. DevTools memory 뷰로 잴 계획만
  남긴다.
