# PERF.md - 병목 분석과 before/after 실측

> 모든 프레임 수치는 **profile 모드**에서 측정했다 (debug는 JIT/assert 비용으로
> 실제보다 훨씬 느리다 - 일반적인 Flutter 성능 측정 관례). 재현 커맨드는 §1, 결과는 §4.
> 설계 결정의 배경과 근거는 [DESIGN.md](DESIGN.md), 여기서는 수치와 그 해석만 다룬다.

## §0. 이 수치가 언제 측정된 것인가

**아래 수치는 이 앱을 포트폴리오 데모로 옮기기 전 빌드에서 측정한 값이고, 이식
이후 재측정하지 않았다.** 성능 문서에서 이 사실을 적지 않으면 독자는 지금 트리의
실측치로 읽는다 - 그래서 먼저 적는다. 이식하며 성능 경로에 생긴 차이는 둘이다:

1. **데이터 소스 교체** ([lib/feed/](lib/feed/)) - 파라미터(2,000종목 / 60Hz /
   배치당 1~250건 / 지연 tick·정지·에러 확률)는 그대로지만 구현과 seed 가 다르다.
   부하의 **성질**은 같고 tick 의 **정확한 수열**은 다르다. §2의 부하 산정(평균
   7.5k/s, 종목당 265ms)은 파라미터에서 나오므로 그대로 유효하고, §5의 기각률
   0.046% 같은 수열 의존 수치는 같은 자릿수일 것으로 보지만 그 값 자체가 재현되는
   것은 아니다.
2. **시총 누적 int -> BigInt** (§5, DESIGN.md §5) - web 타깃의 정밀 상한 때문이다.
   §2 분해표에서 이 항목은 적용 비용의 4.4%이고, 종목당 곱과 델타는 여전히 int
   연산이며 BigInt 는 tick 당 덧셈 1회다. 그래도 **이 변경 이후의 측정값은 없다.**

재현 커맨드(§1)는 그대로 동작하므로, 지금 트리의 수치가 필요하면 직접 돌리면 된다.
수치를 새로 적을 때는 이 절도 함께 갱신할 것.

## §1. 측정 방법 - 재현 가능성

### 결정론적 입력

`MarketFeed`를 `start()` 대신 **`pump()`** 로 구동한다. 기본 seed
고정이므로 baseline/개선본/스윕 구성이 **바이트 단위로 동일한 tick 수열**
(지연/역순 tick, 거래정지 포함)을 받는다. 시나리오는
[integration_test/perf_test.dart](integration_test/perf_test.dart) 하나이며,
앱 부팅 시 repository가 구독을 걸어둔 뒤 pump하므로 "리스너가 붙어야 방출"
조건을 항상 만족한다.

### 시나리오 (5구간, 워밍업 60배치는 측정 제외)

| 구간 | 내용 | 부하 성격 |
|---|---|---|
| `idle` | 정지 화면에 200배치(약 3.3초 분량) 주입 | 순수 tick 반영/집계 비용 |
| `scroll` | fling 12회 x 각 16배치 주입 | 스크롤(행 mount/unmount) + tick 동시 |
| `idle15k` | 프레임당 배치 2개 x 200프레임 (약 초당 15,060건) | feed 상한 부하 (§6-2) |
| `search` | `ㅎㅂ` 필터 적용 상태로 200배치 (한빛* 그룹 = 전체의 1/16) | 필터 상태에서의 tick 반영 |
| `detail` | 상세 화면을 띄운 채 150배치 (개선본 전용 - baseline은 상세 없음) | 구독 수명 관리 효과 |

### 지표

엔진 `FrameTiming` 콜백에서 구간별로 수집:
- **build**: UI 스레드 프레임 구성 시간 (avg / p50 / p90 / p99 / worst, ms)
- **raster**: 래스터 스레드 시간 (avg / p90 / worst, ms)
- **jank**: build 또는 raster가 16.7ms(60fps 예산)를 넘은 프레임 수/비율

### 재현 커맨드

```bash
# baseline -> 개선본 -> 통지 주기 스윕 순서로 5회
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/perf_test.dart -d macos --profile \
  --dart-define=BASELINE=true          # baseline
# (define 없이)                        # 개선본, 통지 주기 0ms
# --dart-define=NOTIFY_MS=50|100|200   # 스윕
```

각 실행이 stdout에 `PERF_SUMMARY {...}`(구간별 지표)와 `STORE_STATS {...}`를
남긴다. §4의 표는 이 라인들을 그대로 옮긴 것이다. **벤치 창은 전면에 유지한 채
측정한다** - 창이 다른 창에 가려지면 macOS가 Metal drawable 공급을 지연시켜
raster 스레드가 수백 ms 단위로 블록되는 측정 환경 아티팩트가 생긴다 (앱 비용이
아님을 창 노출 상태를 바꿔가며 확인했다).

### 측정 환경

macOS 15.7.8 / Intel Core i7-9750H(6C12T) / 16GB / Flutter 3.44.9(stable) /
Dart 3.12.2 / macOS desktop 타깃, profile 모드. 열 스로틀링이 있는 노트북이므로
절대값보다 **동일 조건 상대 비교**가 의미의 중심이다. (최초 측정은 3.29.2에서
했고, 3.44.9로 올린 뒤 전 수치를 재측정해 이 문서를 갱신했다 - 결론이 바뀐
항목은 없다.)

## §2. 부하 특성 분석 - 병목은 연산이 아니라 rebuild 전파

최적화 전에 부하의 자릿수부터 계산했다. feed 파라미터(60Hz, 배치당 1~250건)에서:

| 항목 | 값 | 계산 |
|---|---|---|
| 평균 tick 유입 | **~7,500건/s** (최대 15,000) | 60Hz x 평균 125.5건 - 실측 600배치에 75,328건(=125.5/배치)으로 일치 |
| 종목당 tick 간격 | 평균 **~265ms** | 7,530 / 2,000종목 = 약 3.8건/s/종목 |
| 화면에 보이는 행 | ~15행 (56px x ~800px 뷰포트) | 보이는-행 갱신은 약 15 x 3.8 = **초당 57건, 프레임당 약 1건** |
| 배치 1개 적용 비용 (본 구현) | **276us** (debug JIT; profile은 그 이하) | 마이크로벤치, 아래 |
| 프레임 예산 대비 | 16.7ms의 **~1.7%** | 276us / 16.7ms |

마이크로벤치 (`flutter test test/micro_bench_test.dart`, 동일 캡처 배치 600개를
두 소비자에 주입 - debug JIT이므로 **상대 비교용**). 단독 실행 4회의 대표값이며
범위는 store 252.0~303.0 / naive 2,995~3,684us다:

```
MICRO_BENCH ticks=75328 batches=600
  store_us_per_batch=275.6      # 본 구현: 정합성 검증+3단 상태+증분 시총+RankIndex 전부 포함
  naiveagg_us_per_batch=3345.2  # 배치마다 시총 전량 재합산 + 2,000건 전체 정렬
  stats=ApplyStats(applied: 75225, rejectedStale: 36, unchanged: 67)
```

### 적용 비용의 내부 분해 - 지배 항목은 하나다

"1~2%면 충분하다"에서 멈추면 튜닝할 곳을 모른 채 끝난다. 같은 입력으로 구성요소를
따로 재봤다 (각 5회 중 최소값, JIT 워밍업 후. 각 항목은 공통 루프(맵 조회+timestamp
검증) 위에 하나씩 얹어 측정했고, 아래 "순수" 열은 거기서 공통 루프를 뺀 값이다):

| 구성요소 | 순수 비용 | 비중 |
|---|---|---|
| **RankIndex 갱신 (SplayTreeSet 제거+삽입)** | 75.1ms | **83.4%** |
| 종목별 notifier 갱신 + 통지 | 5.0ms | 5.5% |
| Quote 할당 + 필드별 변경 비교 | 4.0ms | 4.4% |
| 시총 델타 누적 (측정 시점 int, 현재 BigInt - §0) | 4.0ms | 4.4% |
| 맵 조회 + timestamp 단조 검사 (공통 루프) | 2.0ms | 2.2% |
| 배치당 top(20) + listEquals | 1.2ms | 1.4% |
| **applyBatch 전체** | **90.0ms** | 149.9us/배치, **1.19us/tick** |

(합이 100%가 아닌 것은 항목별 측정 오차 1.4%다. 전체값이 위 마이크로벤치보다
낮은 것은 이 표가 5회 반복 중 최소값(워밍업 후)이기 때문이다.)

두 가지가 드러난다. 첫째, **순위 유지가 적용 비용의 약 83%**이고 나머지 다섯을 전부
0으로 만들어도 17% 남짓밖에 줄지 않는다 - 최적화 손잡이는 사실상 하나뿐이다(§6-3).
둘째, 행 리스너를 20개 붙여도 90.0ms -> 87.6ms로 **차이가 노이즈 수준**이다. 통지
대상 수는 이 경로의 비용이 아니며, 병목이 연산이 아니라 rebuild 전파라는 §2의 전제가
적용 경로 내부에서도 확인된다.

**결론(가설)**: 순수 연산은 증분 유지 시 프레임 예산의 1~2%로, 병목일 수 없다.
전량 재계산 경로조차 배치당 3.3ms(debug)다. 그렇다면 baseline이 느린 이유는
연산이 아니라 **(1) 배치마다 화면 전체를 rebuild 대상으로 만드는 setState 전파,
(2) 그 build 안에서 다시 하는 전량 재계산, (3) RepaintBoundary 부재로 인한 넓은
repaint**여야 한다. 이 가설이 맞다면 "전파를 차단"한 개선본은 연산을 더 빠르게
만들지 않고도 프레임을 회복해야 한다 - §4가 이를 검증한다.

## §3. baseline -> 개선본: 무엇을 바꿨고 왜 그 항목인가

baseline([lib/baseline/baseline_page.dart](lib/baseline/baseline_page.dart))은
비교 기준의 정의 그대로다: 배치마다 `setState()` 전체 rebuild, 매 build 시총
전량 재합산/Top-20 전체 정렬/검색 전량 재스캔(초성 재추출 포함), 행에
RepaintBoundary/itemExtent 없음, timestamp 검증 없음, tiebreak 없음.

| # | 개선 항목 | 대체한 baseline 동작 | 겨냥한 병목 |
|---|---|---|---|
| 1 | 종목별 `ValueListenable` 구독 (행당 1구독) | 페이지 전체 setState | 배치당 rebuild 범위: 화면 전체 -> 값이 바뀐 보이는 행만 |
| 2 | 행 `RepaintBoundary` + `itemExtent` 고정 | 경계 없음 | 행 1개 텍스트 변경이 목록 레이어 전체를 다시 그리는 것 차단, 스크롤 layout 상수화 |
| 3 | 시총 합계 정수 델타 누적 | 매 build 2,000건 재합산 | build 경로에서 O(n) 제거 (+부동소수 오차 원천 제거) |
| 4 | `RankIndex` (SplayTreeSet, O(log n)/tick) | 매 build 2,000건 정렬 | build 경로에서 O(n log n) 제거, 동률 tiebreak로 rank thrashing 제거 |
| 5 | Top-20 통지를 "순서 변경 시만" | 매 배치 스트립 rebuild | 순위 불변 프레임의 스트립 build 0회화 |
| 6 | 검색 정적 인덱스 + debounce 120ms | 매 build 전량 매칭(초성 재추출) | 필터 비용을 tick 경로에서 완전 분리 (질의 변경 시에만) |
| 7 | 상세 진입 시 통지 범위 제한 | (baseline 상세 없음) | 상세 화면 동안 목록 rebuild 비용 0 |
| 8 | 값 불변 tick 통지 생략 | 무조건 setState | halted 반복/clamp 고착 tick의 무의미한 rebuild 제거 |

정합성 장치(timestamp 기각/3단 상태/에러 복구)는 성능 항목이 아니지만 **같은
경로 위에** 있다 - §2의 276us는 이들을 전부 포함한 비용이다. 즉 "정합성을
지키느라 성능을 냈다"가 아니라, 정합성 포함 적용 비용 자체가 예산의 1%대다.

## §4. 결과 - before/after 실측

> 아래 수치는 §1 커맨드의 출력(`PERF_SUMMARY` 라인)을 그대로 옮긴 것이다.
> 단위: ms. jank = build 또는 raster > 16.7ms인 프레임.

### 4-1. baseline vs 개선본 (통지 주기 0ms)

| 구간 | 구성 | 프레임 | build avg | p50 | p90 | p99 | worst | raster avg | raster p90 | raster worst | jank% |
|---|---|---|---|---|---|---|---|---|---|---|---|
| idle | baseline | 202 | **8.05** | 7.61 | 10.95 | 14.90 | 16.67 | 1.09 | 1.45 | 2.61 | 0.5 |
| idle | **개선** | 271 | **2.38** | 1.48 | 6.32 | 9.24 | 9.52 | 1.07 | 1.37 | 2.36 | 0.0 |
| scroll | baseline | 867 | 2.77 | 1.44 | **9.46** | 13.45 | 26.82 | 1.03 | 1.36 | 3.59 | 0.23 |
| scroll | **개선** | 872 | 1.65 | 1.44 | **4.05** | 9.27 | 12.98 | 1.12 | 1.52 | 2.53 | 0.0 |
| idle15k | baseline | 203 | **9.09** | 9.07 | 11.32 | 13.47 | 14.38 | 1.15 | 1.43 | 2.80 | 0.0 |
| idle15k | **개선** | 237 | **5.36** | 4.09 | 8.45 | 49.49 | 96.93 | 1.20 | 1.61 | 2.68 | 2.53 |
| search | baseline | 279 | **6.10** | 7.12 | 9.86 | 15.01 | 18.39 | 1.15 | 1.38 | 26.10 | 1.08 |
| search | **개선** | 278 | **2.76** | 1.88 | 6.75 | 12.06 | 13.64 | 1.31 | 1.68 | 2.19 | 0.0 |
| detail | **개선** | 384 | **0.57** | 0.25 | 0.99 | 3.16 | 13.80 | 2.80 | 1.56 | 129.69 | 2.34 |

**build(UI 스레드) - 이번 최적화가 겨냥한 지표:**

- **idle: 8.05 -> 2.38ms (-70%).** baseline은 배치마다 전체 rebuild + 전량
  재계산으로 프레임 예산(16.7ms)의 48%를 상시 소모한다. 개선본은 14%.
  이 데스크톱(i7)에서는 둘 다 대체로 60fps가 나오지만, 모바일 AP에서는 이
  5.7ms 차이가 그대로 jank 마진이다 - 그리고 baseline은 이 비용을 **화면이
  조용해도** 낸다.
- **scroll: p90 9.46 -> 4.05ms (-57%).** 행 mount/unmount가 겹치는 구간에서
  꼬리가 절반 이하로 줄었다 (itemExtent 고정 + 행 단위 구독의 효과).
- **idle15k(유입 2배, 초당 15,060건): p50 9.07 -> 4.09ms (-55%), avg 9.09 ->
  5.36ms.** 상한 부하에서도 개선본이 평상시 baseline(8.05ms)보다 낮다. 개선본
  avg에는 아래에서 다루는 스파이크 6프레임이 포함되어 있어 p50이 부하의
  대표값에 더 가깝다. 부하를 2배로 올렸을 때 두 구성이 서로 다르게 반응하는
  구조는 §6-2에서 따로 다룬다.
- **search: avg 6.10 -> 2.76ms (-55%).** baseline은 매 build 전량 매칭(초성
  재추출 포함)을 하고, 개선본은 정적 인덱스라 필터가 tick 경로에 비용을 얹지
  않는다.
- **detail: build avg 0.57ms.** 상세 화면이 떠 있는 동안 목록 통지를 정지한
  효과로, idle(2.38ms) 대비 -76% - "화면 뒤 목록의 갱신 비용이 유지되지
  않아야 한다"는 요구의 실측 증거다. p50은 0.25ms로, 프레임 대부분이 사실상
  아무 일도 하지 않는다.

**raster는 양쪽 구성 모두 평균 1.0~1.3ms로 예산에 한참 못 미친다** (행 단위
RepaintBoundary의 효과 - 값이 바뀐 행의 텍스트 레이어만 다시 그린다). 단발
스파이크는 성격이 갈린다: baseline search의 raster 26.1ms 1프레임은 필터 적용
순간의 전체 재구성이고, detail의 129.7ms 1프레임은 화면 전환 순간 drawable
재획득으로 재현마다 위치가 다른 측정 환경 잡음이다(§1의 창 전면 유지 주의 참조).
개선본 idle15k의 build p99/worst(49.5/96.9ms, 237프레임 중 6개)는 이 세션에서
새로 관측된 스파이크인데, 상태 계층의 상한 부하 비용이 배치당 531us(§6-1)라
연산으로는 자릿수가 설명되지 않고 raster도 그 구간에서 평온하다(worst 2.68ms).
창 전면 유지 스크립트의 주기적 재활성화 같은 외부 스톨로 추정하지만 이번
세션에서는 재현 검증을 하지 못했으므로, 수치는 표에 그대로 두고 p90(8.45ms,
예산 안)을 꼬리의 대표값으로 읽는다. 그 6프레임을 제외하면 개선본의 jank는
전 구간 0%이고, baseline은 idle/scroll/search에서 0.2~1.1%의 jank가 실제로
발생한다 - 이 차이도 개선 격차의 일부다.

### 4-2. 통지 주기 스윕 - 성능-신선도의 선을 실측으로 긋기

`NOTIFY_MS = 0 / 50 / 100 / 200` (0 = 배치 도착 즉시 통지). 신선도 상한은
"주기 + 1프레임"이므로 200ms 구성은 요구(<=200ms)를 정의상 초과한다.

| notifyMs | 구간 | build avg | p90 | p99 | worst | 신선도 상한 |
|---|---|---|---|---|---|---|
| **0 (채택)** | idle | 2.38 | 6.32 | 9.24 | 9.52 | **약 16ms** |
| 50 | idle | 2.86 | 9.94 | 15.91 | 17.91 | 약 66ms |
| 100 | idle | 1.06 | 5.29 | 9.92 | 10.38 | 약 116ms |
| 200 | idle | 0.80 | 0.32 | 10.63 | 12.03 | 약 216ms - **요구 위반** |
| **0 (채택)** | scroll | 1.65 | 4.05 | 9.27 | 12.98 | 약 16ms |
| 50 | scroll | 1.69 | 3.06 | 9.67 | 11.83 | 약 66ms |
| 100 | scroll | 1.36 | 2.38 | 10.67 | 19.49 | 약 116ms |
| 200 | scroll | 1.24 | 2.27 | 9.73 | 11.88 | 약 216ms - 요구 위반 |
| **0 (채택)** | idle15k | 5.36 | 8.45 | 49.49 | 96.93 | **약 16ms** |
| 50 | idle15k | 2.07 | 7.97 | 10.67 | 13.51 | 약 66ms |
| 100 | idle15k | 1.74 | 9.13 | 14.69 | 18.20 | 약 116ms |
| 200 | idle15k | 1.06 | 0.25 | 13.31 | 14.92 | 약 216ms - 요구 위반 |
| **0 (채택)** | search | 2.76 | 6.75 | 12.06 | 13.64 | **약 16ms** |
| 50 | search | 1.49 | 5.88 | 8.69 | 17.38 | 약 66ms |
| 100 | search | 1.14 | 5.59 | 11.37 | 22.99 | 약 116ms |
| 200 | search | 0.81 | 0.39 | 10.62 | 11.14 | 약 216ms - 요구 위반 |

읽는 법 - 주기를 키우면 **build 평균은 내려간다**(0->200ms에서 idle
2.38->0.80, idle15k 5.36->1.06: 60Hz 요약/Top-20 rebuild가 모이는 효과). 반면
**꼬리(p99/worst)는 이 이득을 따라오지 않는다** - 한 번의 flush에 여러 배치
분량의 통지가 몰리기 때문에, 모아서 flush하는 구성들(50~200ms)에서도 worst
11.1~23.0ms의 스파이크가 사라지지 않고 오히려 예산을 넘는 프레임이 생긴다
(idle 50ms 17.9, scroll 100ms 19.5, search 100ms 23.0ms). 이번 세션은
run-to-run 잡음이 커서(§7) 이전 세션처럼 "주기에 비례해 꼬리가 단조로
나빠진다"까지는 단정하지 않지만, 방향은 같다: 주기를 키워서 사는 것은 평균이고,
파는 것은 신선도(최대 12배)와 꼬리 예측 가능성이다. **어느 구성도 평상시 프레임
예산을 위협하지 않는 상황에서 신선도가 가장 좋은 0ms를 채택**했다 -
DESIGN.md §4의 "즉시 통지 = 프레임 정렬 coalescing" 논지의 실측 근거다.

단, 스윕은 다음 손잡이가 어디인지도 보여준다: 요약 영역이 지금보다 무거워져
build 평균을 낮춰야 하는 날이 오면, 첫 수단은 `NOTIFY_MS=50`이다 (idle15k avg
-61%, 신선도 상한 66ms로 여전히 요구의 1/3). 이 판단이 코드 변경 없이 빌드
플래그로 가능하도록 남겨두었다.

(detail 구간은 채택 구성에서만 잰다. 통지 주기를 키우면 상세 화면에서 프레임
자체가 희소해져 표본이 드로어블 대기 아티팩트로 뒤덮이고, 애초에 이 구간은 통지 주기가
아니라 구독 수명 관리의 효과를 보는 자리라 스윕 비교 대상이 아니다.)

## §5. 스토어 통계 - 정합성 장치의 실측 개입률

시나리오 전체(워밍업 포함, idle15k 때문에 배치 수가 구간별로 다르다)의 `STORE_STATS`:

| 구성 | 측정 구간 | applied | rejectedStale (역순 기각) | unchanged (값 불변) |
|---|---|---|---|---|
| NOTIFY_MS = 0 | idle15k + search + **detail** | 152,299 | 70 | 100 |
| NOTIFY_MS = 50 | idle15k + search | 132,513 | 62 | 87 |
| NOTIFY_MS = 100 | idle15k + search | 132,513 | 62 | 87 |
| NOTIFY_MS = 200 | idle15k + search | 132,513 | 62 | 87 |

- **역순 tick 기각률 0.046%** (70/152,469): 지연 tick은 드물지만 실재하며,
  기각하지 않으면 그 70번마다 가격/거래량이 과거로 튀는 화면이 된다.
  버리는 정보량은 무시 가능한 수준 - "timestamp 단조 강제" 정책의 비용이
  사실상 0임을 뜻한다.
- **값 불변 tick 100건**: 통지/집계를 모두 건너뛴 건수. 처음에는 "clamp(±30%)
  고착이 누적되는 장시간 세션일수록 커질 것"으로 예상했으나, 200초 분량 soak
  실측(`soak_test.dart`, 150만 tick)이 이를 **반증**했다 - 완전 불변은 전/후반
  485 vs 476건으로 늘지 않는다(전체의 0.06%). 가격이 고착되어도 거래량은 계속
  변하기 때문에, clamp 고착은 완전 불변이 아니라 **"가격 고착 + 거래량 변동"
  버킷에 쌓인다: 298,200건, 전체 tick의 ~20%**다. 이 20%가 필드별 변경 플래그
  (§3-8)의 실측 근거다 - 행 통지만 하고 시총 델타/순위 갱신을 건너뛰므로,
  전체 tick의 1/5에서 rank 갱신(적용 비용의 약 83%, §2)이 사라진다.
- **통지 주기가 다른 세 구성의 통계가 완전히 동일**하다는 것이 이 표의 핵심
  결론이다: 같은 입력(seed 고정)에 대해 상태 계층의 결과가 **통지 정책과 무관**하게
  바이트 단위로 같다 - "정합성은 도착 즉시, 화면 전파만 제어"(DESIGN.md §1)
  라는 분리 불변식이 측정으로 검증된 셈이다. 성능 튜닝(통지 주기)이 정합성을
  건드릴 수 없는 구조라는 뜻이기도 하다.

## §6. 부하 상한(15,000건/s)에서의 여력

feed 의 전제는 "초당 최대 약 15,000건"인데, **seed가 실제로 내는 평균은 그 절반이다.**
배치 크기가 `1 + Random.nextInt(250)`(1~250 균등)이라 평균 125.5건 x 60Hz = 약 7,500건/s이고,
15,000건/s는 배치가 상한 근처를 뽑은 프레임에서만 순간적으로 스친다. §4의 수치는 그
"평균 7.5k/s + 상한 스파이크" 부하에서의 측정이므로, 상한이 **지속**될 때의 여력은
따로 재야 한다. 두 갈래로 쟀다.

### 6-1. 합성 상한 부하 - 상태 계층 단독 (재현 5초)

[test/throughput_test.dart](test/throughput_test.dart): 250건짜리 배치 600개
(= 60Hz 기준 10초 분량, 총 150,000 tick)를 스토어에 직접 주입한다. **이 배치는 seed가
만든 수열이 아니라 합성 부하다** - seed는 읽기만 하고 수정하지 않되, 상한값을 지속시키려면
tick을 직접 만드는 수밖에 없기 때문이다. 화면에 뜨는 행 수만큼(20개) 리스너를 붙인다.

```
THROUGHPUT_15K ticks=150000 batches=600 total_ms=318
  us_per_batch=530.9   ns_per_tick=2123   cpu_pct_of_one_core=3.19
```

단독 실행 4회 범위는 496.8~576.0us/배치, 한 코어의 **2.98~3.46%**다 (60Hz에서는
"배치당 비용 / 프레임 예산"과 "CPU 점유율"이 같은 값이 된다). debug(JIT) 값이므로
profile에서는 이보다 낮다 - 즉 이 수치는 **상한선**이다.
같은 테스트가 배치당 비용이 프레임 예산의 1/4을 넘으면 실패하는 회귀 가드를 겸한다.

"여유롭다"는 어디서 깨지는지 알 때만 의미가 있어서, 유입을 계속 올리는 스윕도
같은 파일에 있다 (`SCALE_SWEEP`): 프레임당 125/250/500/1,000/2,000건
(7.5k~120k건/s 상당)에서 배치당 189/461/767/823/1,024us. 배치가 커질수록 tick당
단가가 오히려 내려가고(고착 가격의 재갱신 비율 증가), **이 유니버스의 물리적 최대
유입 - 전 종목이 매 프레임 갱신되는 120k건/s - 에서도 프레임 예산의 6%다.**
상태 계층의 포화점에는 배치 크기로는 도달할 수 없다는 뜻이고, 그래서 스케일
한계는 유입이 아니라 종목 수 축에 있다 (DESIGN.md §10의 "종목 20만 개" 행).

### 6-2. 진짜 seed 수열로 상한 재현 - 프레임 레벨

합성 부하는 tick의 성질(지연/역순, 정지)이 빠진다. 그래서 벤치에 `idle15k` 구간을 두어
**프레임당 배치를 2개씩** 밀어 넣는다: 125.5건 x 2 x 60프레임 = 약 **초당 15,060건**이,
seed가 만든 진짜 수열 그대로 들어온다. seed는 손대지 않는다 - 소비 쪽에서 `pump(2)`를
부를 뿐이다.

> 단서: feed 내부 시계는 배치당 +16ms이므로 이 구간은 **가상 시간이 2배로 흐른다**
> (벽시계 1초 = feed 기준 2초). 부하 재현이 목적이며, 신선도 예산은 벽시계 기준
> 그대로다.

| 구성 | 유입 | build avg | p50 | p90 | p99 | worst |
|---|---|---|---|---|---|---|
| baseline | 7.5k/s (`idle`) | 8.05 | 7.61 | 10.95 | 14.90 | 16.67 |
| baseline | **15k/s (`idle15k`)** | 9.09 | 9.07 | 11.32 | 13.47 | 14.38 |
| 개선 | 7.5k/s (`idle`) | 2.38 | 1.48 | 6.32 | 9.24 | 9.52 |
| 개선 | **15k/s (`idle15k`)** | **5.36** | **4.09** | 8.45 | 49.49 | 96.93 |

상한 부하에서도 개선본의 build는 p50 4.09ms(예산의 25%), p90 8.45ms로 예산 안이다
(avg 5.36에는 §4-1에서 다룬 스파이크 6프레임이 포함되어 있다 - p99/worst는 그
프레임들의 값이며, 외부 스톨 추정과 재검증 못 한 한계까지 §4-1에 적어 두었다).
두 구성의 반응 차이가 구조를 드러낸다 - baseline은 부하가 2배가 되어도
8.05 -> 9.09ms(+13%)로 크게 움직이지 않는다. tick 수와 무관하게 매 프레임
화면 전체를 다시 만들기 때문에 이미 비용의 천장에 붙어 있는 것이다. 개선본은
p50 기준 1.48 -> 4.09ms로 부하에 비례해 늘어난다. 실제로 바뀐 것만 갱신하니
당연하고, 그럼에도 **상한 부하의 개선본이 평상시 baseline(8.05ms)보다 낮다.**

### 6-3. 그래서 어디를 고쳤나 - RankIndex tiebreak

§2의 분해가 손잡이를 하나로 특정했다: **순위 유지가 적용 비용의 약 83%**. 그 안에서
비교자는 갱신 1회당 O(log n)회 호출되는 가장 뜨거운 코드였고, 거기서 종목코드
**문자열 비교**를 하고 있었다. 이것을 생성 시 1회 계산한 **정수 순위**로 바꿨다
(등락률도 `compareTo` 대신 원시 비교). 순서 규약은 그대로다.

측정 -> 변경 -> 재측정 순으로, 같은 갱신열(가격이 실제로 바뀐 60,311건)을 두 구현에
교차로 먹여 비교했다 (구 구현은 하네스에 원형 그대로 복제해 동일 조건에서 실행):

| | 갱신 1회 | 갱신열 전체(60,311회) |
|---|---|---|
| 문자열 tiebreak (before) | 1,349ns | 81.3ms |
| **정수 tiebreak (after)** | **1,165ns** | **70.3ms** |
| 차이 | **-13.6%** | -13.6% |

순위 유지가 적용 비용의 약 83%이므로 적용 경로 전체로는 약 -11%에 해당한다.

동치성은 눈으로 확인할 성질이 아니라서 테스트로 못박았다
([test/rank_index_test.dart](test/rank_index_test.dart)): 코드 배열이 사전순으로 들어오지
않는 경우(정수 tiebreak가 index가 아니라 코드 순위를 따라야 한다)와 동률이 대량 발생하는
무작위 3,000회 갱신 fuzz를, 매번 **문자열 비교 전체 정렬**과 대조한다.

**그럼에도 이 최적화는 현 부하에서 불필요한 여력이다.** 상한 부하 기준 한 코어 3%
언저리에서 8%를 덜어내는 것은 프레임을 하나도 더 살리지 못한다 - §4의 어떤 구간에서도
이 차이는 측정 노이즈에 묻힌다.
반영한 이유는 다른 데 있다: 비용이 **생성 시 O(n log n) 한 번 + 정수 배열 하나**로 끝나고,
지배 항목이 하나로 특정된 상태에서 그 항목의 상수를 줄여 두는 것이 종목 수가 늘 때 남는
유일한 여유이기 때문이다. 반대로 **채택하지 않은 것**은 상위 K 후보 구조다 - 순위 정확성을
전순서로 보장하는 현재 성질을 잃고 등가성 테스트가 성립하지 않게 되는데, 그 대가를
2%짜리 문제에 지불할 이유가 없다 (DESIGN.md §10의 "종목 20만 개" 행에 재검토 조건으로 남겼다).

### 6-4. 남은 손잡이

분해표 기준으로 순위 유지를 제외한 전부(통지/할당/시총/조회)를 0으로 만들어도 약 20%다.
다음 실질적 손잡이는 순서대로 (1) 상위 K 후보 구조로 트리 크기 축소, (2) 집계 통지 주기
분리(§4 말미), (3) 파생 계산이 무거워질 경우의 isolate 오프로딩(DESIGN.md §8-3)이며,
셋 다 **현 부하에서는 근거가 없다.** 근거가 생기는 조건은 각 항목에 적어 두었다.

## §7. 한계와, 더 쟀다면

- **단일 머신/단일 실행**: run-to-run 편차(열 스로틀링, OS 스케줄링)를 통계
  처리(N회 반복/신뢰구간)하지 않았다. 구성 간 격차가 자릿수 수준이라 결론이
  뒤집힐 여지는 작다고 판단했고, 반복 실행 스크립트는 §1 커맨드로 대체된다.
- **macOS 데스크톱 측정**: 모바일 GPU/스레드 모델과 raster 특성이 다르다.
  기기 실측이 필요하면 같은 커맨드에 `-d <기기>`만 바꾸면 된다 (시나리오/seed
  동일). iOS 시뮬레이터는 raster 경로가 달라 성능 측정에 쓰지 않았다.
- **가상 키보드/IME 미개입**: `enterText`는 IME 조합 비용을 우회한다. 초성
  검색의 실사용 타이핑 부하는 debounce(120ms)가 흡수하므로 결론에 영향이
  없다고 판단했다.
- **메모리 프로파일 생략**: 고정 자료구조(notifier 2,000개, 링버퍼 180) 중심이라
  누수 위험이 낮다고 보고 프레임에 시간을 썼다. DevTools memory 뷰로 잴 계획만
  남긴다.
