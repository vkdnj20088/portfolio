# k8s - 다중 인스턴스 실험실

**이것은 배포가 아닙니다.** 라이브는 여전히 EC2 한 대 위의 nginx + systemd 이고, 그 구성은
[`infra/`](../infra/) 에 있습니다. 이 디렉터리는 배포를 대신하지 않습니다.

여기 있는 이유는 하나입니다. 작업 릴레이 워커 코드에 이런 주석이 있습니다.

> `SELECT ... FOR UPDATE SKIP LOCKED` … 잠긴 행을 건너뛰므로 워커 여럿이 같은 작업을 두 번
> 집지 않는다 - 이 성질은 Testcontainers IT 가 실제 MySQL 로 실증하고, **운영 배포는 단일
> 인스턴스라 워커 1개만 쓴다**(안 쓰는 능력을 켜 두지 않는다).

즉 **코드에 있지만 한 번도 켜 본 적 없는 능력**입니다. 켜 볼 자리가 필요했고, 배포 서버를
늘리지 않고 켜 보려면 클러스터를 잠깐 세웠다 지우는 수밖에 없습니다. kind 클러스터는 로컬에서도
CI 에서도 몇 분 만에 태어나 몇 분 뒤 사라집니다.

문서에 쓸 수 있는 문장은 이것뿐입니다.

> 라이브 배포는 단일 인스턴스라 워커를 하나만 씁니다. 다중 인스턴스 안전성은 CI 에서 kind
> 클러스터에 파드 둘을 띄워 검증하고, 그 결과를 수치로 남깁니다.

## 무엇이 도는가

| 워크로드 | 역할 | 복제 |
|---|---|---|
| `mysql` (StatefulSet) | 공유 상태. 리스·낙관적 락·UNIQUE 제약이 전부 여기 있다 | 1 |
| `guard-web` (Deployment) | 요청을 받는다. 워커는 꺼져 있다 | 2 |
| `guard-worker` (Deployment) | 큐를 돈다. 요청은 받지 않는다 | 2 |
| `loandoc` (Deployment) | 첫 파드 실습용. 이미 Dockerfile 이 있어 가장 빨리 뜬다 | 1 |

웹과 워커가 **같은 이미지, 다른 환경변수**입니다. 역할을 갈라야 각각을 따로 늘리고 따로
재배포할 수 있습니다.

```bash
./k8s/scripts/lab.sh up        # 클러스터 + 이미지 + 배포
./k8s/scripts/lab.sh measure   # 실험 전부 실행 → k8s/results/runs.json
./k8s/scripts/lab.sh down      # 클러스터 제거
```

로컬과 CI 가 **같은 스크립트**를 돕니다. 사람이 손으로 kubectl 을 두드려 얻은 숫자는 다음
사람이 재현할 수 없고, 재현할 수 없는 숫자는 포트폴리오에 적을 수 없습니다.

## 재현 조건

로컬(Intel Mac)에서는 컨테이너 런타임이 필요합니다.

```bash
brew install colima docker kubectl kind
colima start --cpu 4 --memory 6 --disk 20
```

CI 는 `helm/kind-action` 이 클러스터를 세웁니다([`.github/workflows/k8s-lab.yml`](../.github/workflows/k8s-lab.yml)).
kind·노드 이미지·kubectl 버전은 로컬과 같은 값으로 못박아 두었습니다(kind v0.32.0 /
`kindest/node:v1.36.1` / kubectl v1.36.4). 두 곳이 서로 다른 클러스터를 돌면 한쪽에서 얻은
숫자를 다른 쪽 이야기로 옮겨 말할 수 없습니다.

## 이 실험실이 앱에 남긴 스위치

전부 기본값이 꺼짐이고, 켜지 않으면 존재하지 않는 것과 같습니다. 문서 QA 의 가드 대조,
이중 승인 실험대의 방어선 토글과 같은 장치입니다 - **주장을 글로만 두지 않으려면 끄는 경로가
있어야 합니다.**

| 속성 | 기본 | 무엇을 위한 것인가 |
|---|---|---|
| `app.relay.worker.lease-mode` | `SKIP_LOCKED` | 리스가 기대는 층을 하나씩 걷어낸다(`FOR_UPDATE` / `NONE`) |
| `app.relay.worker.lease-hold-ms` | `0` | 리스 커밋과 실행 커밋 사이의 취약 구간을 넓힌다 |

## 실측 결과

전부 `k8s/results/runs.json` 에 있고, 아래 표는 그 파일을 읽은 것입니다. 그 파일은
`measure` **한 번**의 결과입니다 - 실행할 때마다 새로 쓰기 때문에, 여러 번의 실행이 섞여
좋은 회차만 남는 일이 없습니다. 숫자는 실행마다 조금씩 다릅니다 - 판정에 쓰는 것은 **건수**
이고 경과 시간은 참고용입니다.

### 1. 파드 둘이 큐를 돈다 - 겹치지 않는가

작업 200건(`ALWAYS_SUCCEED`), 워커 2 파드, 폴 간격 20ms, 모드마다 3회.

| 리스 모드 | 성공 | 겹쳐 기록된 시도 | 리스 경합 | 경과 중앙값 | 파드 분배(3회) |
|---|---|---|---|---|---|
| `SKIP_LOCKED` (기본) | 200/200 | **0** | 0, 0, 0 | 9.5s | 99/101 · 135/65 · 66/134 |
| `FOR_UPDATE` | 200/200 | **0** | 0, 0, 0 | 9.8s | 55/145 · 70/130 · 158/42 |
| `NONE` (잠금 없음) | 200/200 | **0** | **19, 40, 33** | 9.7s | 137/63 · 103/97 · 99/101 |

읽는 법이 셋입니다.

- **정확성은 세 모드 모두 유지됐습니다.** 흔히 하는 말 - "SKIP LOCKED 를 빼면 중복 처리가
  난다" - 은 이 코드에서 **거짓**입니다. 행 잠금을 아예 빼도 겹쳐 기록된 시도는 0입니다.
  아래 층이 잡기 때문입니다.
- **무엇이 잡았는지는 리스 경합 수가 말합니다.** 잠금을 뺀 모드에서만 19~40회 걸렸습니다.
  둘이 같은 행을 집었고 낙관적 락(`version`)이 한쪽을 되돌린 횟수입니다. 되돌린다는 것은
  그 틱을 통째로 버린다는 뜻이라, 정확성이 아니라 **낭비**로 값을 치릅니다.
- **경과 시간은 세 모드를 가르지 못합니다.** 처음 1회씩만 쟀을 때는 19.7s 대 11.9s 로
  두 배 가까이 갈렸는데, 3회로 늘리자 중앙값이 9.5 / 9.8 / 9.7 로 붙었습니다(0.3초 차이).
  같은 모드 안의 흔들림이 그보다 훨씬 큽니다 - `NONE` 은 9.5s 와 26.0s 가 같은 모드에서
  나왔습니다. 첫 측정의 차이는 잡음이었고, 그것을 성질이라고 적지 않으려고 반복을 넣었습니다.

파드 분배가 158/42, 66/134 처럼 크게 쏠리는 회차가 모드와 무관하게 나옵니다. 리포지토리
주석이 `SKIP LOCKED` 의 쏠림 가능성을 예고해 두었지만, **이 표본으로는 그 성질 때문이라고
말할 수 없습니다** - 다른 모드에서도 같은 폭으로 나오기 때문입니다.

### 2. 워커를 죽이면 - 이 실험실의 이유

[이중 승인 실험대](../portfolio_react_next/apps/docqa/src/app/approval)는 정직 패널에
"크래시를 실제로 주입하지 않았습니다 - 멈춘 상태를 저장소에 직접 만들어 흉내 냈습니다"라고
적어 두었습니다. 여기서는 진짜로 죽입니다.

| 항목 | 값 |
|---|---|
| 작업 | 60건 |
| 죽인 시점에 리스를 쥐고 있던 작업 | 5건 |
| 죽인 뒤 `RUNNING` 으로 남은 작업 | **5건** |
| 워커를 되살리고 45초 더 기다린 뒤 | **5건 (그대로)** |

**회수 경로가 없다는 것이 실측으로 확인됐습니다.** 리스는 짧은 트랜잭션으로 `RUNNING` 을
커밋한 뒤 작업을 실행합니다. 그 사이에 프로세스가 죽으면 그 작업은 `RUNNING` 에 남는데,
`leaseReady` 는 `PENDING`/`RETRYING` 만 집으므로 아무도 다시 집지 않습니다.

여기까지 오는 데 네 번 틀렸고, 그 과정이 결과의 일부입니다.

1. 24건에 한 번 죽였더니 0건. 창이 마이크로초라 못 맞힌 것을 "구멍이 없다"로 읽을 뻔했습니다.
2. 200건에 네 번 죽여도 0건. 여전히 못 맞혔습니다.
3. 창을 3초로 넓혀도 0건. `kubectl` 왕복 지연이 그보다 길었습니다.
4. 창을 30초로 넓히고 **리스를 쥔 순간** 워커를 전부 죽여서야 맞았습니다.

창을 넓힌 것은 계측 장치(`lease-hold-ms`)이고 **죽이는 것은 여전히 외부의 강제 종료**입니다.
창의 존재 자체는 코드의 성질이지 실험이 만든 것이 아닙니다.

### 3. 롤링 업데이트와 프로브

| 실험 | 요청 | 실패 |
|---|---|---|
| 롤링 업데이트 중 (`maxUnavailable: 0` + preStop 5초) | 516 | **0** |
| readiness·startup 프로브를 뺀 배포 | 41 | **26** |

요청 수가 달라 비율로 봐야 합니다 - 프로브를 빼면 배포 중 요청의 **3분의 2**(41건 중 26건)가
실패했습니다.
JVM 이 아직 기동 중인 파드가 준비됐다고 표시되어 트래픽을 받았기 때문입니다.

### 4. 동시 기동 마이그레이션

파드 둘이 같이 뜨면 Flyway 가 마이그레이션을 **번갈아** 적용합니다(한 파드가 V4·V6·V8,
다른 파드가 V3·V5·V7). 락이 마이그레이션 하나 단위라 그렇습니다. 결과는 정확합니다 -
8개가 각각 한 번씩, 실패 0, 중복 0.

## 이 실험실이 증명하지 않는 것

- **같은 물리 머신입니다.** kind 노드 셋은 도커 컨테이너 셋이고 커널을 공유합니다.
  네트워크 분단, 노드 하드웨어 장애, 존 장애는 이 구성으로 다룰 수 없습니다.
- **MySQL 이 한 대입니다.** 이 실험이 보려는 것은 DB 의 HA 가 아니라 **앱이 여럿일 때**의
  안전성이라 복제를 두지 않았습니다. 복제 지연이 만드는 문제는 여기 없습니다.
- **부하가 작습니다.** 200건 규모이고, 이 숫자로 처리량이나 지연을 말하지 않습니다.
- **라이브가 아닙니다.** 배포는 여전히 단일 인스턴스이고, 여기서 켠 능력은 배포에서 꺼져
  있습니다. 이 실험실이 말하는 것은 "켜도 된다"이지 "켜져 있다"가 아닙니다.
- **회수 경로는 아직 없습니다.** 2번 실험이 구멍을 숫자로 확인했을 뿐, 고치지 않았습니다.
  고친다면 이중 승인 실험대가 쓴 방법 - 멈춘 리스를 '모름'으로 회수해 조회로 푸는 것 -
  이 그대로 대응됩니다.
